## 〇、本项目落地状态（先读这一节，否则会写错）

现存代码与架构文档**不是同一代**：

| | 遗留实现（已存在） | 目标架构（未开始） |
|---|---|---|
| 表 | `gb_org` / `gb_device` / `gb_device_channel` / `gb_platform` / `gb_parent_platform` / `gb_platform_share` … | `res_*` / `out_*` / `sync_*`，**尚未建表** |
| 包 | `com.solo.gb28181` / `media` / `onvif` / `system` / `openapi` / `websocket` | 按 3.3.2 的包边界新建 |

三条纪律：

1. 新架构代码**新建包**，不得往 `gb_*` 表上叠加新语义。旧模块只读参考，不重构。
2. **会话不是表**。GB28181 会话是 Redis 对象（`GbInviteSession` / `CascadeSendSession`），见 C21b。禁止为会话建表。
3. 遗留实现里的写法**不能当范例**：它有 `gb_device_channel` 单表混装多来源、`gb_platform_share` 直接删行等与本文冲突的做法。

## 一、数据模型

### C1 资源三类一表，"来源"是列不是拆表（3.5.1）
组织 / 设备 / 通道各一张表。`source_type` **只有两个取值**：`NATIVE`（本平台）/ `INBOUND`（同步进来）；具体来源平台在 `source_platform_id`（NATIVE 时为 0）。

> ✗ 错法：把平台 ID 存进 `source_type`（写成 `source_type='5'`）；或按来源拆成 `res_channel_native` / `res_channel_inbound`。

### C2 业务键唯一，禁止用自增 id 当跨平台主键（3.5.2）
唯一键 `uk_src(source_type, source_platform_id, code)`。跨平台识别、共享、点播一律用业务键定位。

> ✗ 错法：用 `id` 做跨平台引用——换一个来源就串行。

### C3 入站资源原地 UPDATE，禁止删除重建（3.6.6、6.3 A 档）
同一业务键重复导入后 `res.id` 必须不变。共享关系、暴露码、播放会话全部挂在 `id` 上。

> ✗ 错法：`DELETE` 后 `INSERT` 重建 → id 变 → 共享指空、上级点播 404。
> 验收：同一业务键导入两次，第二次走 UPDATE 且 id 与第一次相同、无重复行。

### C4 主键雪花；资源状态四态；软删留痕（3.5.2、3.8.4）
`status` 取值 `ACTIVE` / `STALE` / `OFFLINE` / `REMOVED`，**默认 ACTIVE**。软删写 `removed_at`，不物理删行。

> 注意：遗留表 `gb_device.status` 默认值是 `OFFLINE`，与新表的 `ACTIVE` 不同，不要混用。

### C5 树用物化路径；通道必须归属组织（3.6）
`res_org.path` 存物化路径，换父必须重写整棵子树。通道的 `org_id` 必须存在且属于同一来源平台——**DB 约束 + 服务层校验双重**，不只靠前端。

## 二、视图与来源

### C6 三棵树互相独立（2.3）
本地组织树 / 各下级平台自带树 / 各上级平台的目录树。资源数据只有一份，三棵树是对同一份数据的**不同分组方式**。

> ✗ 错法：把下级平台的组织物理挂进本地组织树；把本地树直接当上级看到的那棵树（会导致"给 A 看重点单位、给 B 看全量"做不到）。

### C7 "转发"是一种动作，不是第四种来源（3.9）
同一条通道在资源池里仍只有一份，转发只改变它被共享到哪个平台。

## 三、同步（入站）

### C8 全量同步走 staging + 三条集合 SQL（3.8.2）
禁止把两边都拉进内存做 diff。百万级镜像只有集合 SQL 这条路。

### C9 SET 列集与 WHERE 差异列集同源生成（3.8.2）
由**同一份**"可变列定义"（如 `MUTABLE_COLUMNS`）派生，禁止两处各写一遍列名。
方言差异：PG `IS DISTINCT FROM` + `UPDATE ... FROM`；MySQL `(a <=> b) = 0` + `UPDATE ... JOIN`。

> ✗ 错法：手工维护两份清单 → 改了一边漏了另一边 → 数据没变却每次全量 UPDATE。
> 验收：同一批数据连跑两次，第二次影响行数为 0。

### C10 三段会话 start / synching / finish（3.8.1）
只有 `finish` 才切换生效，`synching` 期间线上读旧数据。
ACK 是**批级**不是轮级；超时按"无进展"（默认 75s）判定，不按总时长。
失败后进冷却窗口（默认 `超时 + 10s`），冷却状态存 Redis，**不放进程内变量**。

### C11 两道删除闸门语义不同，禁止混用（3.8.3、3.8.4）
**前置规则**：上游返回空目录 = 异常，**不触发消失计算**，必须人工二次确认才允许清空。

| 闸门 | 条件 | 动作 |
|---|---|---|
| G1 空批保护 | 本轮暂存 0 行但本地该平台有 N 行 | **整轮失败回滚**，`task=FAILED`，`SYNC_EMPTY_STAGING`。新增/更新**同样不生效** |
| G2 批量删除保护 | 预计删除数 > 本地行数 × `delete_guard_ratio`，且本地 > 1000 行 | **只跳过删除**，新增/更新照常，摘要明写"删除已跳过"，并给二次确认入口 |

跳过状态必须在 **台账 / 任务详情 / 事件推送** 三处可见。

> ✗ 错法：把 G1 做成"只跳删除"（丢批场景会产生一半新一半旧的脏镜像，比清库更难查）；把 G2 做成整轮失败。

### C12 资源消失的联动必须同事务四步（3.8.4）
1. `res_*` 置 `REMOVED` + `removed_at`
2. `out_share.ref_alive = 0`（**所有**受影响平台；**不删行**）
3. 每个受影响平台各插一条 `outbox(DELETE)`（**按平台聚合，不按通道发散**）
4. `out_code_map.state = TOMBSTONE`

恢复路径：上游重现 → `ref_alive` 置回 1 + 生成 `ADD` 事件 + **复用该资源自己的墓碑码**；不同资源之间序号**永不复用**。
点播与对账都必须校验 `ref_alive`（DELETE 推送成功前上级可能仍在点播，此时必须直接拒绝）。

> ✗ 错法：直接 `DELETE out_share` 行——丢掉"这个通道曾共享给谁"，恢复要人工重配。

### C13 组织四步回填顺序不可调换（3.8.2）
1. `parent_code` = 本轮已落库的组织编码 → 挂该组织
2. 历史绑定恢复（`device_org_binding`）→ 挂绑定组织，并继续参与后续同步
3. `parent_code` = 来源平台的域编码 → 挂该来源的根组织
4. 都不命中 → 挂 `[未分类]`，保留 `ACTIVE` 并打标 `org_missing`

第 4 步的影响行数 = 本轮异常设备数，**必须进摘要并在界面高亮**。
配套：组织缺失设备的延迟重试（默认 30s 防抖、超 10 分钟强制触发一次、本轮成功收尾后取消计划）。

### C14 staging 不是旁路，审计才是旁路（3.13.3）
- staging 写失败 → **本轮必须失败**（返回失败，不静默丢数据）。
- 审计/快照 → 异步单线程池、队列满可丢、可整体关闭（`sync.audit.enabled=false`）；但收尾任务**必须预留队列位**，否则轮次永远停在 `RUNNING`。

> ✗ 错法：两处都写成 `try/catch` 吞掉。

## 四、共享（出站）

### C15 资源写与 Outbox 插入同事务（3.9.5）
同一个 `@Transactional` 内既写 `res_*` 又 `insert outbox`，禁止事务外发消息。

### C16 暴露码规则：域10 + 类型3 + 序号7（3.9.3）
序号按平台单调分配，删除不复用（墓碑保留）。编码一经分配**不随资源变化**。

> ✗ 错法：在国标 20 位码**尾部追加字符**避冲突——会破坏校验位并被上级拒绝。冲突时只动序号段重分配。
> 上级拒绝同码节点时**不自动改码**（会让上级产生孤儿节点），记 `last_error` 转人工。

### C17 出站事实独立建 publish_round 台账（6.4）
与入站 `sync_round` 同口径、**不同表**，禁止混用。一个是入站事实，一个是出站事实。

## 五、事件分发

### C18 事件只带定位，不带全量（3.11.7）
超量降级两形态：`CHANGED_DETAIL` / `REFRESH_ALL`，阈值 `event_detail_max` 默认 500。
单轮待推 > 阈值时合并为一条 `REFRESH_ALL` + 引用快照，**不做逐条循环**。

### C19 事件可以合并，游标不能跳号（3.11.7）
降级时也必须发出一条事件**占住游标**，否则客户端重连会永久落后。

## 六、多级级联与转发

### C20 四道防环，保存时与投递前双重执行（3.10.2）
1. 反向共享：目标平台 ID == 资源的 `source_platform_id`
2. 来源链：目标平台 ID ∈ 资源 `origin_chain`
3. 跳数：`hop_count + 1 > maxHop`（默认 3）
4. 自身域：资源码前 10 位 == 本平台 SIP 域，但 `source_platform_id != 0`

命中任一 → **保存时直接拒绝**并给明确文案（"该资源来自平台 A，不能再共享回 A"），不等推送失败。

### C21 两级媒体串联三条硬约束，缺一必埋僵尸会话（3.11.5、6.6）

**a) SDP 由本平台构造**
回给上级的 200 OK，`o=` / `c=` 必须是**本平台对外可达地址**，解析顺序 `gb28181.cascade.sdp-public-ip` → `MediaServer.streamIp` → `hostIp`（实现：`CascadeSdpAddress.resolve`）；`m=` 是本平台发送端口，**禁止透传下级/来源的 SDP 地址**。落 `sdpRewritten=true` 供回归断言。
解析结果为空 / `0.0.0.0` / `127.0.0.1` / `::1` / `localhost` 时**回 500 拒绝本次点播并回收已拉起的取流**；显式配置了非法值**不回退到节点 IP**（配错必须暴露）；解析到私网地址只打 WARN。
UDP 与 TCP-passive 时端口**也必须 > 0**（RFC 4566 中端口 0 表示"禁用该媒体流"，与 `a=sendonly` 矛盾）：回 200 前从发送端口段预分配并写进 SDP，ACK 后按同一端口 `startSendRtp`；该端口被 ZLM 报占用时换端口重试（最多 3 次）并 WARN，接受"实际源端口 ≠ SDP 里的 `m=`"——非端口类错误不重试。
上级 SDP 里的 `c=` / `m=` 只用于 `startSendRtp` 的**目的地址**，`y=` 的 SSRC 只用于回 SDP 的 `y=`（两者必须一致）。

**b) 两侧 SSRC 分别落在两个 Redis 会话对象上，靠 srcStream 关联**
禁止建"转发会话表"：

```
GbInviteSession（来源侧：本平台 → 设备/下级）
  streamId / ssrc / rtpPort / serverId
                          │  CascadeSendSession.srcStream = streamId
CascadeSendSession（上级侧：上级 → 本平台）◄─┘
  sendStreamId / ssrc(= 上级 SDP 的 y=) / dstIp / dstPort / localSendPort
```

索引 `cascade:send:by_src:{srcStream}` 是 **Set**（1 源流 : N 上级）。加字段改 JSON 模型即可，**不需要 DDL**。

**c) 按源流判活，不靠信令**
`GbInviteSession.lastRtpTime` 是僵尸判定唯一依据，**由本平台巡检采样回写**。ZLM `getMediaList` 没有"最后收流时刻"：`createStamp` 与 `aliveSecond` 都是**流的创建时刻**，可用的只有 `bytesSpeed`、`readerCount` / `totalReaderCount`（早期文档写的 `origin_stamp` 不存在，已废弃）。因此定时任务（10s 一轮，`GbHealthScheduledTasks.sweepCascadeZombieSources`）采样 `bytesSpeed > 0` 即刷新 `lastRtpTime`（最小写间隔 5s，避免每轮重写整个会话 JSON）；`= 0` 保持旧值。

判定五档（`GbInviteLiveness.probe`，宁可漏判不可误杀）：流不在节点上 → `GONE`（进阈值判定）；`bytesSpeed > 0` → `FLOWING`（刷新时间戳）；`= 0` 且有人观看 → `WATCHED`（**不判死**，HLS 拉流 / 暂停 / 切片刷新都有瞬时 0）；`= 0` 且没人看 → `SILENT`（进阈值判定）；节点不可达（`getMediaListOrNull` 返回 `null`）→ `UNREACHABLE`（本轮整体放行，一次抖动不能把所有会话当僵尸清掉）。同一路流 ZLM 按 schema 各返回一条，`bytesSpeed` 与 readers 都**取最大值**。只有 `READY` 的 `PLAY` / `PLAYBACK` 参与判死（`INVITING` 还没起流；`DOWNLOAD` / `RECORD` 是 TCP 文件流，本就没有连续 RTP）。

超阈值（`lastRtpTime` 为空时退回 `readyTime` 起算）后按 `by_src` 取出 Set，逐个**先 `stopSendRtp` 再发 BYE**（仅 `toTag` 非空时发），最后清来源侧 ZLM RTP server 与 SSRC。**顺序不能反**——反了会出现"BYE 已发、推流还在"的窗口。阈值首版只有全局 `gb28181.cascade.rtp-timeout-sec = 30`（≤ 0 关闭巡检）；`platform.rtp_timeout_sec` 按上级覆盖暂缓（`gb_parent_platform` 无该列）。

### C22 每跳独立互斥与冷却（6.6）
同一通道的入站会话与各出站会话**各持一把锁**，禁止共用通道级锁——否则上游一个断线会把所有上级的点播一起锁住。

## 七、运行保障

### C23 台账与快照不是一档（3.13.1、3.13.2、6.3 B/C 档）
| | 默认 | 保留 | 定位 |
|---|---|---|---|
| `sync_round` | **开启** | 长期 | 对账依据，必须落盘 |
| `sync_round_snapshot` | **关闭** | 最近 2 轮 | 排障证据，100 万通道 × 2 轮 ≈ 400MB，是单库体积唯一会翻倍的来源 |

必须落盘 `delete_skipped` 与当时的 `guard_ratio`，否则两周后没人能回答"那天为什么没删"。

### C24 互斥与冷却状态放 DB/Redis，禁止放进程内变量（3.13.5）
多实例下进程内标志位互相看不见，结果是"每个实例都认为自己空闲"，重复同步同时发生。
同平台互斥 = DB 唯一约束（`platform_id` + `status=RUNNING`）+ 分布式锁；跨平台并发上限 = 信号量（默认 3）。

### C25 闸门阈值默认 0（关闭），首次接入必须手工设 0.2（3.8.4）
阈值依赖各平台规模，没有通用安全值。**首次接入、以及大版本升级后的第一次全量，必须手工设为 0.2（20%）**。台账记录当时阈值，可回查。

## 八、边界与安全

### C26 业务边界（2.6）之外一律不做
播放内核、存储、智能分析等超范围项单独立项。看到"顺手实现一下"的冲动，先停下来确认。

### C27 信任边界：每个入口单独校验，不继承上一道关卡的结论（3.12.1、3.12.4、3.12.7）
六类边界：入站信令 / 入站点播 / 管理 API / 对外订阅 / 出站推送 / 媒体面。
入站 SIP 摘要鉴权；管理 API 强制 HTTPS + HSTS；SSE 强制 HTTPS + IP 白名单；RTP 不加密但校验来源 IP。
**ZLM 的 HTTP-FLV / WebSocket 直连等于绕过全部共享授权**，前端必须经本平台换取短期播放凭证（与 `out_share` 命中绑定，默认 10 分钟）。

### C28 GB35114 国密级联：首版不要求，建表即带占位（附录 B #13）
**已定稿，不要再问。** `platform_credential` 保留 5 个可空字段，`cipher_suite` 默认 `'NONE'`。
后续若要求，需重估四处：鉴权链路、SDP 加密、证书管理、媒体加密。

## 九、冲突上报（硬性流程）

实现过程中若发现某条约束**落地不了**，或工程惯例与它冲突：

1. **停止编码**；
2. 输出【冲突上报】区块：冲突的是哪一条 C、为什么不适用、两种以上可选方案、你的建议；
3. 等人类确认后，**先改架构文档、再同步改本文件**，最后才改代码。

禁止的做法：在代码里偷偷绕开、加一个 `if (特殊场景) return;`、或"先这样，之后再对齐"。

> 进度与接口签名台账见项目根 `PROGRESS.md`。
