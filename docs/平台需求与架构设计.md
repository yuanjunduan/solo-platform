# 第 1 部分　原始需求整理

## 1.1 一句话概括

平台由三块组成：**本地资源**（自己维护）、**下级平台**（把别人的资源收进来）、**上级平台**（把自己的资源送出去）。三块的资源在系统里是"同一批数据的不同来源"，但操作权限完全不同：只有本地资源能改，收进来的和送出去的都只读。

## 1.2 三类资源与角色

| 角色 | 平台在本系统中的位置 | 资源来源 | 本地能否改/删 |
|---|---|---|---|
| 本地资源 | 自己 | 本平台录入 | **能**（新增/修改/删除） |
| 下级平台 | 上游，向本平台推目录 | 海康、大华等外部平台 | **不能**（只读镜像） |
| 上级平台 | 下游，接收本平台推送 | 本平台推送给它 | **不能**（在上级侧同样只读） |

## 1.3 下级平台（数据入站）

### 2.1 资源汇聚
- 主要目标：把外部海康、大华平台的**组织、通道**同步到本地。
- 同步过来的**组织、设备、通道没有修改、删除操作**（纯只读）。
- 组织有父子关系，可自动组装成**目录树**。
- **通道必须属于某个组织**（不允许游离通道）。

### 2.2 事件分发（规划项）
- 其他平台可以通过 **SSE / WebSocket** 获取"指定下级平台"的**组织与通道**数据。

## 1.4 上级平台（数据出站）

### 3.1 共享范围
- 把**本地的组织、通道**，以及**从其他平台获取的组织、设备**，共享给上级平台（海康、大华）。
- 共享出去的**组织和设备、通道没有修改、删除操作**。
- 本地组织、设备、通道的具体维护放在"本地资源"里做（见 4）。

### 3.2 转发（级联穿透）
- 从其他平台同步过来的组织、设备、通道，可以**再通过本平台推送给一个或多个上级平台**。

### 3.3 多上级维护
- 维护多个上级平台信息，这部分已经具备。

## 1.5 本地资源

- 组织、设备、通道支持**新增、修改、删除**，自主维护。
- 本地资源可以**推送到上级平台**给别人用。
- 本地资源要能支撑现有业务：实时播放、录像回放、云台控制等。

## 1.6 从需求里能直接读出的硬约束

| 编号 | 约束 | 影响 |
|---|---|---|
| C1 | 只有本地资源可写 | 写操作必须在服务端统一拦截，不能只靠前端隐藏按钮 |
| C2 | 通道必须属于组织 | 通道入库前必须有组织归属，否则拒绝或落到兜底组织 |
| C3 | 下级组织树必须完整挂载 | 父节点缺失时要补建占位父节点，不能出现"孤儿树" |
| C4 | 同一资源可推给多个上级 | 每个上级有独立的目录视图与编码空间 |
| C5 | 下级资源可二次转发 | 出站选资源时不能只认"本地资源"，要认"来源" |
| C6 | 对外分发只给指定下级平台 | 订阅必须按平台维度做授权，不能全量暴露 |

# 第 2 部分　需求理解与技术澄清

## 2.1 我的理解（一句话）

> **一个资源池，三个入口。**
> 所有组织/设备/通道都存在同一个资源池里，每条数据带一个"来源"标签（本地 / 来自某下级平台）。
> 下级平台页 = 往池子里**灌数据**；上级平台页 = 从池子里**挑数据往外发**；本地资源页 = 自己**维护数据**。
> 资源池本身不区分"这是谁的"，只记录"来自哪"，权限和展示按来源决定。

这样设计的好处：你 3.2 的"转发"需求不需要额外开发——因为下级同步来的资源本来就在同一个池子里，上级平台页只要允许选中它即可。

## 2.2 三条数据流

```
① 入站（下级平台 → 本平台）
   外部平台 ──注册/目录查询/变更通知──► 接入层 ──► 目录镜像 ──► 资源池(来源=平台X)
                                                        └──► 组装成"平台X"的目录树

② 出站（本平台 → 上级平台）
   资源池(任意来源) ──共享编排──► 该上级的虚拟组织树 ──► 目录推送/变更推送 ──► 上级平台

③ 分发（本平台 → 第三方）
   资源池(来源=平台X) ──变更事件──► SSE/WS ──► 订阅方
```

关键点：**② 的输入是"资源池任意来源"，不是"只看本地"**。这是 3.2 转发需求的实现基础。

## 2.3 八个关键判断（含与行业做法的对照）

| # | 判断 | 理由 | 行业对照 |
|---|---|---|---|
| J1 | 三类资源**一张表 + 来源字段**，不建三套表 | 转发需求要求同一资源能同时被本地业务、多个上级消费；三套表会导致同步/映射爆炸 | 国标平台普遍用"设备表 + 来源"实现多级级联 |
| J2 | 通道用**组织路径**约束，不只存 org_id | 下级平台组织可能多层，只存直接父组织无法回答"这个通道在哪个目录下"；播放鉴权、共享选范围都靠路径 | GB28181 目录项天然是 ParentID 链条 |
| J3 | 组织**不直接推**给上级，映射成该平台的**虚拟组织（215/216）** | 上级只认扁平 DeviceID+ParentID 目录，且不同上级要看到不同组织形态 | GB/T 28181 附录 D 虚拟组织规范 |
| J4 | 入站资源**全字段只读**（含展示名） | 按你的原话执行。预留"本地显示名覆盖"作为后置可选，不放进首版 | 部分平台允许本地别名，属增强非必需 |
| J5 | 出站用**编码映射表**（原始码 ↔ 暴露码） | 多个下级平台的通道码可能重复，直接透传会让上级点错通道 | 国标级联的标准做法 |
| J6 | 变更推送走**本地消息表（Outbox）+ 定时对账**，不用事件直发 | 上级断网、重启、丢订阅时，事件直发必然漏推且无法补救 | 分布式系统标准模式（Transactional Outbox） |
| J7 | 对外分发只推**变更事件 + 序号**，全量走快照接口 | 通道量大时全量塞进 WS 会打爆连接，且客户端无法增量更新 | 事件溯源/订阅的通用做法 |
| J8 | 入站同步**串行 + 可取消 + 有进度**，不做并发全量 | 万级通道并发同步会打爆外部平台，且失败难以重入 | 目录同步的稳妥做法 |

## 2.4 需求里的歧义与我的处理

| 歧义点 | 你的原话 | 我的处理 |
|---|---|---|
| 下级"设备"是否也要同步 | 2.1 只提"组织、通道" | **必须同步**：GB28181 里通道一定挂在设备下，没有设备通道无处安放。但 UI 上**默认按组织 → 通道展示**，设备只在通道详情里出现，不单独占一列菜单 |
| 下级资源能不能改展示名 | "组织和设备、通道没有修改删除操作" | 首版**全部只读**。如果后续需要"本地别名"，做成独立字段 `local_name`，同步不覆盖它 |
| 上级平台侧的"没修改删除"指谁 | 3. "组织和设备、通道没有修改删除操作" | 理解为**本平台不能改上级侧的数据**（本来也改不到）。本平台对"我要推什么"当然可增删（那是共享编排，属于配置不是资源） |
| 3.1 "放到第 4 个下一个说明" | 指本地资源的维护 | 上级平台页**不提供资源编辑入口**，选中本地资源时给"去本地资源维护"的跳转链接 |
| 转发时组织怎么处理 | 3.2 未说明 | 默认**按下级平台的组织树一键生成**该上级的虚拟组织树，也允许手工调整层级（见 5.4） |
| "通道必须属于某个组织"是谁的组织 | — | 是**它自己平台上那个组织**（下级平台的组织），不是本地组织。本地的树和下级平台的树是两棵并列的树 |

## 2.5 明确不做的事（控制范围）

1. 不做"本地组织"与"下级组织"的自动融合（两边并列展示，避免语义混乱）。
2. 不做跨平台的资源编辑回写（下级改了就是下级的，本平台不反向写）。
3. 首版不做多协议级联（海康 ISUP、大华私有协议）的实际对接，只把接口留出来。
4. 首版不做资源池的全文检索集群，通道量 > 20 万再考虑。

# 第 3 部分　总体架构

## 3.1 五条架构原则

| 原则 | 落地方式 |
|---|---|
| **一个资源池** | 组织/设备/通道各一张主表，带 `source_type` + `source_id` |
| **来源决定权限** | 服务端写入口统一判定 `source_type == NATIVE` 才放行 |
| **视图与数据分离** | 出站目录、SSE 事件都是"视图"，不产生第二份资源数据 |
| **协议可替换** | 入站/出站各自一个适配器接口，GB28181 只是其中一种实现 |
| **状态可观测** | 同步、推送、订阅三类过程都有持久化状态与失败原因，全部可在页面看到 |

## 3.2 逻辑分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ 接入层      SIP 信令(5061) │ HTTP API(8080) │ WebSocket │ SSE         │
├──────────────────────────────────────────────────────────────────────┤
│ 协议适配层  InboundAdapter(GB28181/预留ISUP)  OutboundAdapter(GB28181)│
│            统一内部模型：Endpoint / CatalogNode / MediaRef            │
├──────────────────────────────────────────────────────────────────────┤
│ 资源域      OrgService │ DeviceService │ ChannelService  ← 唯一事实源  │
│ 入站域      EndpointRegistry │ CatalogSyncService │ MirrorTreeBuilder │
│ 出站域      ShareOrchestrator │ VirtualOrgBuilder │ CodeMapper        │
│            │ CatalogPublisher │ ReconcileService                     │
│ 分发域      EventHub → SseHub / WsHub │ SubscriptionService           │
├──────────────────────────────────────────────────────────────────────┤
│ 基础设施    MySQL │ Redis(会话/锁/在线态) │ MinIO(录像) │ ZLM(媒体)    │
└──────────────────────────────────────────────────────────────────────┘
```

**只有"资源域"能写资源表**。入站域、出站域都只能通过 ResourceService 的方法改数据，禁止各自直接 UPDATE，这样权限判定只有一处。

## 3.3 统一编目模型

三类节点共用一个结构，差异用字段表达：

| 字段 | 组织 ORG | 设备 DEVICE | 通道 CHANNEL |
|---|---|---|---|
| `id` | 本地主键 | 本地主键 | 本地主键 |
| `code` | 组织编码 | 设备国标码 | 通道国标码 |
| `parent_code` | 上级组织 | 所属组织 | 所属设备/分组 |
| `path` | `/a/b/c/` | `/a/b/c/` | `/a/b/c/code` |
| `source_type` | NATIVE / INBOUND | 同 | 同 |
| `source_id` | 来源平台ID | 同 | 同 |
| `name` / `local_name` | 原始名 / 本地别名（预留） | 同 | 同 |
| `status` | — | 在线/离线 | 在线/离线 |
| `capability` | — | 厂商/型号/IP/协议 | 云台/对讲/录像 |

好处：左树、搜索、共享选题器、SSE 事件都能用**一套代码**处理三种来源、三种节点。

## 3.4 入站同步时序

```
外部平台           本平台接入          同步服务            资源域
   │  REGISTER ──────►│                   │                  │
   │◄──── 200 OK ─────│ 登记端点(在线)     │                  │
   │  Catalog查询 ───►│                   │                  │
   │◄─ Catalog响应 ───│─ 入队(平台,全量) ─►│                  │
   │                  │                   │ 1.落 staging 表   │
   │                  │                   │ 2.补建缺失父节点 ─►│
   │                  │                   │ 3.按业务键 upsert─►│
   │                  │                   │ 4.标记消失节点删除 │
   │                  │                   │ 5.更新同步快照版本 │
   │◄─ 订阅(可选) ────│                   │                  │
   │  Notify(增量) ──►│───────────────────►│ 单条 upsert       │
```

要点：
- **先写 staging 再合并**：全量同步先落到临时表，全部成功后再事务合并，避免"同步一半失败"导致目录残缺。
- **业务键 upsert**：`(source_id, code)` 唯一，重复同步幂等。
- **消失判定**：本次全量里没出现、且上次出现过的节点 → 标记删除（软删 + 延迟清理），并触发事件。
- **父节点补建**：报文里 ParentID 指向不存在的节点时，建一个 `占位` 组织，保证树不断链。

## 3.5 出站共享时序

```
配置阶段（人工，一次）
  选资源（本地组织 / 本地通道 / 某平台的通道）
    → 生成或调整该上级的虚拟组织树
    → 建立共享项（资源 ↔ 虚拟组织节点 ↔ 上级平台）
    → 写编码映射（必要时分配暴露码）

运行阶段（自动，持续）
  资源变更事件 ─► 找到"哪些上级需要知道" ─► 写 Outbox
                                              │
                          ┌───────────────────┘
                          ▼
                   投递器（按平台分片）
                   PENDING → 发送 → 200 → SENT
                            └ 失败 → FAILED(退避重试)
                            └ 平台离线 → 暂停该平台队列
  定时对账：期望目录快照 vs 上次快照 → 差异补投 → 差异过大则全量重推
```

## 3.6 转发（3.2 需求）如何实现

**不需要新链路**，只需要把"选资源"的数据源从"本地"扩大到"资源池全量（含入站）"，再加两条规则：

1. **来源标注贯穿**：转发到上级的目录项里，通道码用该上级的暴露码；但本平台内部保留 `source_id`，用于：上级点播时知道要 INVITE 哪个下级平台、下级离线时自动给上级推离线状态。
2. **两级媒体串联**：上级点播转发通道 → 本平台向上级 INVITE 回 SDP → 同时向下级平台 INVITE 拉流 → 转封装推给上级。会话表记录"上游会话 ID ↔ 下游会话 ID"，任一侧断开发动另一侧 BYE。

## 4.2 关键表 DDL 草案

### 资源池：组织

```sql
CREATE TABLE catalog_org (
  id            BIGINT       NOT NULL COMMENT '本地主键',
  code          VARCHAR(32)  NOT NULL COMMENT '组织编码/下级组织ID',
  parent_code   VARCHAR(32)  NULL COMMENT '父组织编码，根为 NULL',
  path          VARCHAR(512) NOT NULL COMMENT '物化路径 /a/b/c/',
  level         TINYINT      NOT NULL COMMENT '层级，根=1',
  name          VARCHAR(128) NOT NULL,
  local_name    VARCHAR(128) NULL COMMENT '本地别名（预留，同步不覆盖）',
  source_type   VARCHAR(16)  NOT NULL COMMENT 'NATIVE/INBOUND',
  source_id     BIGINT       NULL COMMENT 'INBOUND 时为 cascade_endpoint.id',
  sort_no       INT          DEFAULT 0,
  deleted       TINYINT      DEFAULT 0,
  update_time   DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_src_code (source_type, source_id, code),
  KEY idx_parent (parent_code),
  KEY idx_path (path(64))
) COMMENT '组织（本地维护 + 下级镜像统一存放）';
```

### 资源池：通道

```sql
CREATE TABLE catalog_channel (
  id            BIGINT       NOT NULL,
  code          VARCHAR(32)  NOT NULL COMMENT '通道国标码',
  org_code      VARCHAR(32)  NOT NULL COMMENT '所属组织编码（硬约束，不允许为空）',
  org_path      VARCHAR(512) NOT NULL COMMENT '所属组织路径，用于子树查询',
  device_code   VARCHAR(32)  NOT NULL COMMENT '所属设备国标码',
  name          VARCHAR(128) NOT NULL,
  local_name    VARCHAR(128) NULL,
  kind          TINYINT      NOT NULL COMMENT '0=通道 1=业务分组 2=虚拟组织',
  status        VARCHAR(8)   NOT NULL COMMENT 'ON/OFF',
  capability    JSON         NULL COMMENT '云台/对讲/录像等能力位',
  source_type   VARCHAR(16)  NOT NULL,
  source_id     BIGINT       NULL,
  deleted       TINYINT      DEFAULT 0,
  update_time   DATETIME     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_src_code (source_type, source_id, code),
  KEY idx_org (org_code),
  KEY idx_org_path (org_path(64)),
  KEY idx_device (device_code)
) COMMENT '通道（含下级目录里的分组行）';
```

**为什么 `source_id` 进唯一键**：两个下级平台各有一个 `34020000001310000001` 时，`(source_id, code)` 才能并存；本地资源 `source_id` 固定为 0。

## 4.3 状态机

| 对象 | 状态 | 流转 |
|---|---|---|
| 入站同步任务 | QUEUED → RUNNING → SUCCESS / FAILED / CANCELED | 失败可重入，从断点继续 |
| Outbox 事件 | PENDING → SENT / FAILED → DEAD | FAILED 退避重试，超上限进 DEAD 并告警 |
| 上级平台 | UNREGISTERED → REGISTERING → ONLINE ↔ OFFLINE | 离线时队列暂停，不消耗重试次数 |
| 暴露码 | ACTIVE → TOMBSTONE | 通道删除后保留墓碑，永不回收序号 |

## 4.4 一致性三道防线

| 防线 | 机制 | 解决什么 |
|---|---|---|
| 第一道 | 写资源 + 写 Outbox **同一事务** | 资源改了但没产生推送任务 |
| 第二道 | 投递器幂等 + 退避重试 + 离线暂停 | 临时网络故障、上级重启 |
| 第三道 | 定时对账（默认 10 分钟） | 事件丢失、逻辑变更、长时间断网 |

对账算法：

```
期望集合 = 当前该上级的共享快照（按 version 排序）
实际集合 = cascade_catalog_ver 记录的上次成功快照
差异 = 期望 - 实际
差异条数 > 阈值（默认 min(200, 总数的 20%)）→ 全量重推
否则 → 差异转 Outbox 补投
对账结果写 cascade_catalog_ver，供页面展示"上次一致时间"
```

# 第 5 部分　关键机制

## 5.1 入站：目录镜像与树组装

1. **平台分组行也是节点**：下级目录里的 215/216 分组在 `catalog_channel`（或独立 `catalog_group`）里存成 `kind=1/2` 的行，通道 `org_code` 指向它。这样"组织树"和"通道挂载"用同一套父子关系，不需要两套树。
2. **树按需组装**：左树懒加载，父节点展开时查 `parent_code`，一次一页（默认 200 条 + `hasMore`）。
3. **占位组织**：报文缺父节点时建 `[占位] 未知分组`，并在详情里标黄提示"上游目录不完整"。
4. **只有通道没有组织的情况**：落到该平台自动生成的 `未分类` 根组织下，界面上用灰色徽标提示，不做静默丢弃。

## 5.2 "只读"怎么做到真的改不了

四层收口，缺一层就会漏：

| 层 | 手段 |
|---|---|
| 路由/权限 | 编辑、删除接口要求 `resource:write` + 资源 `source_type=NATIVE` |
| 服务层 | `ResourceService.assertWritable(id)` 统一守卫，入站资源抛业务异常（带友好文案） |
| 数据层 | 入站资源不由用户请求路径写入，只由同步任务写入 |
| 界面层 | 入站节点不渲染编辑按钮，改为"详情/订阅状态"；被权限拦截时 toast 说明原因而非报 403 |

同时提供一个**只读原因说明**：详情页顶部横幅"该通道由 平台「海康 A」同步而来，协议属性由上游维护"。

## 5.3 出站：本地组织 → 虚拟组织映射

三种建组方式，覆盖你提的所有场景：

| 方式 | 适用 | 操作 |
|---|---|---|
| 手工搭建 | 需要精细控制 | 在"共享编排"里手动建 215/216 层级 |
| **按本地组织一键生成** | 共享本地资源 | 勾选本地组织 → "生成为虚拟组织" → 自动建同构树，通道批量挂载 |
| **按下级平台组织一键生成** | 3.2 转发 | 勾选某平台的某组织 → 生成 → 自动带过来该组织下所有通道 |

规则：
- 生成是**一次性快照**，之后两边独立演进（本地组织改名不会自动改上级的虚拟组织），避免"悄悄改掉上级的目录"。
- 需要联动时，用"重新生成预览"：显示差异（新增/改名/移除），确认后按差异更新。
- 每个上级的虚拟组织树独立，同一通道可在 A 上级挂在"园区/一号楼"，在 B 上级挂在"重点单位"。

## 5.4 转发的两条硬规则

1. **授权不叠加**：本平台对下级资源的转发，不要求下级平台"同意"，但必须在共享项里记录 `ref_source_id`，用于审计"这条通道来自谁、转给了谁"。
2. **状态跟随**：下级通道离线 → 本平台自动给所有转发它的上级推 `STATUS=OFF`；下级平台整体断连 → 推该平台下所有通道离线（合并成一条列表通知，不逐条刷）。

## 5.5 变更推送：增量、断网续传、抖动抑制

| 机制 | 做法 |
|---|---|
| 增量 | 只推变化的目录项（`ADD/UPDATE/DELETE/STATUS`），带 `version` |
| 顺序 | 单平台内 `seq_no` 单调；上级侧按 `version` 取大，乱序也能收敛 |
| 合并 | 同一对象短时间多次变更，投递前合并为最终状态（避免 1 万设备上下线风暴） |
| 断网续传 | 平台离线时队列停摆；恢复注册后按 seq 顺序补发；积压超窗口（默认 5000 条或 24 小时）降级为全量重推 |
| 失败可见 | Outbox 的 `last_error` 直接在"推送监控"页展示，支持单条重试/跳过/导出 |
| 死信 | 重试超限 → DEAD，页面红点提示，人工处理后才消除 |

## 5.6 SSE / WebSocket 分发（规划项的实现要点）

- **职责**：SSE 面向外部集成（单向、可自动重连、穿代理友好）；WS 面向需要双向的场景（如控制指令回执）。
- **订阅模型**：`topic`（catalog / status / alarm）+ `scope`（平台ID 或组织路径），订阅时校验权限，不满足直接 403。
- **事件格式**：`id` = 全局序号（可直接作为 `Last-Event-ID` 续传）；`data` 只带定位信息 + 变更类型 + 版本，明细由客户端按需查。
- **续传**：断线重连带游标，服务端从游标补发（Redis 保留 24h）；补不上返回 409 + 快照地址，客户端全量重建。
- **背压**：单连接队列上限（默认 1000），超限丢弃最旧并发 `lagged` 事件，提示客户端转快照。
- **多实例**：事件经 Redis Stream 扇出，各实例只推自己持有的连接。

# 第 6 部分　交互与体验设计

## 6.1 信息架构（建议替换现有"下级级联 5 项 / 上级级联 7 项"的双份菜单）

现在的问题：组织管理、设备管理在下级和上级各有一套，同一个概念出现两次，运维要记两套路径。

```
资源中心
 ├ 本地组织        ← 可编辑
 ├ 本地设备        ← 可编辑
 ├ 本地通道        ← 可编辑，含播放/云台
 └ 资源总览        ← 三来源汇总只读视图（排障用）

下级平台
 ├ 平台与接入      ← 平台列表 + 准入名单 + 端点登记（一个列表搞定）
 ├ 汇聚目录        ← 左树（各平台并列）+ 右通道列表，纯只读
 └ 同步记录        ← 任务进度 / 差异 / 失败明细

上级平台
 ├ 平台管理        ← 多个上级，注册状态
 ├ 共享编排        ← 选资源 → 建虚拟组织 → 推送（核心页）
 ├ 推送监控        ← 待推送 / 失败 / 重试 / 上次对账时间
 └ 编码映射        ← 暴露码查看与冲突处理

平台配置
 ├ 本平台参数      ← SIP / 媒体 / 编码规则
 └ 事件订阅        ← SSE/WS 订阅方管理（规划）
```

一个原则：**每个资源只在一个地方维护，其他页面只能"选"不能"改"**。

## 6.2 统一页面骨架（三个页面长得一样）

```
┌ 顶部：[本地] [下级] [远程] [全部]   ← 域切换，决定左树内容与右侧过滤
├──────────────┬──────────────────────────────────────────────┐
│ 左侧目录树    │ 右侧列表                                      │
│ 248~280px    │ 搜索框 + 状态筛选 + 表格 + 分页                │
│ 懒加载        │ 行内操作随来源变化                            │
└──────────────┴──────────────────────────────────────────────┘
```

三处保持一致的细节：
1. **来源徽标**：每个节点/行末尾一个小 chip（`本` / `海康A` / `共享`）。颜色只做辅助，文字必须可读。
2. **只读锁**：入站节点带锁图标，hover 提示"由「海康A」同步，只读"。
3. **树内搜索**：左树顶部有搜索框（服务端搜索，支持 10 万节点），输入即过滤并展开命中路径。

## 6.3 下级平台页

- 平台卡片：在线状态、通道数、最后同步时间、**同步按钮**。
- 同步时：行内进度（`63% · 1240/1980`）+ 可取消；完成后 toast 带"查看差异（+12 / ~3 / -1）"。
- 目录树默认**只展开到平台层**，不预加载全部，避免首屏卡顿。
- 通道列表双击 → 播放（只读资源也能播放，这是最常见的诉求，不能因为只读就禁掉）。
- 空态文案：`该平台尚未推送目录 · 立即同步` / `上游返回 0 个组织，请确认对方是否已配置目录`。

## 6.4 上级平台页（共享编排是关键）

一屏三段式，从左到右：

```
① 选资源（多选树）        ② 目标虚拟组织树        ③ 结果预览
   本地组织                 该上级的 215/216       新增 12 / 移除 3
   本地通道                 支持新建/拖拽           冲突 1（点开处理）
   海康A 的通道  ← 转发      一键生成（从①的结构）    预计 10s 内同步
```

- **转发入口就在 ①**：不需要单独做一个"转发"页面，选资源时按来源分组展示即可。
- **一键生成**：①选中的是组织时，②自动镜像出同构树，用户可再调整。
- **冲突处理**：暴露码冲突时在 ③ 列出，给三个选项（自动加后缀 / 手工指定 / 跳过），支持"全部按推荐处理"。
- **推送监控**：每平台一行 `待推送 12 · 失败 3 · 上次一致 10:03`，点开看 Outbox 明细，支持单条重试。

## 6.5 本地资源页

就是现在的组织/设备/通道管理，但补两点：
- 通道列表增加"已共享到"列（显示 `A平台、B平台`，点击跳共享编排），让用户知道"这条通道现在谁在看"。
- 通道详情增加"来源"区块：本地显示 `本地维护`；入站显示 `来自 海康A / 园区1`（只读页复用同一组件）。

## 6.6 反馈与状态规范

| 场景 | 规范 |
|---|---|
| 操作成功 | toast 3 秒自动消失，带结果数量（`已推送 12 条，预计 10 秒内生效`） |
| 操作失败 | 必须给出"下一步做什么"，不要只显示异常堆栈（`上级未注册，已加入待推送队列，注册后自动补发`） |
| 长任务 | 一律有进度 + 可取消 + 可离开页面（后台继续） |
| 只读拦截 | 不返回 403，返回 200 + 业务错误码，toast 说明原因 |
| 危险操作 | 删除组织/设备、清空共享范围 → 二次确认 + 影响面（`将移除 3 个上级的 128 条共享`） |

## 6.7 排障路径（运维最需要的三条）

1. **"设备为什么注册不上"**：准入名单 + 端点登记 + 注册日志 → 必须在同一页。
2. **"上级为什么看不到某通道"**：通道详情"已共享到" → 若为空，给"配置共享"按钮；若有，跳到推送监控看是否 FAILED。
3. **"上级目录为什么和本地不一致"**：推送监控 → 对账差异（期望 N / 实际 M）→ 一键补推。

# 第 7 部分　实施路线

## 7.1 分期

| 阶段 | 目标 | 交付内容 | 验收标准 |
|---|---|---|---|
| **M1 资源池打底** | 一个池子能存三种来源 | 统一编目表 + 来源字段 + 写权限收口 + 本地组织/设备/通道页 | 入站数据无法通过任何接口改写；本地资源播放正常 |
| **M2 入站闭环** | 下级目录能同步、能看、能播 | 端点登记、全量同步（staging + 合并 + 差异）、左树懒加载、同步记录页 | 1 万通道同步 < 5 分钟；中断可续；树完整无孤儿 |
| **M3 出站闭环** | 本地资源能共享到多个上级 | 共享编排（含一键生成）、虚拟组织、编码映射、Outbox 投递、推送监控 | 上级能拉到正确目录并点播；断网恢复后自动补齐 |
| **M4 转发** | 3.2 需求 | 选资源支持入站来源、两级媒体串联、状态跟随 | 下级通道转发后上级可播；下级离线上级收到离线通知 |
| **M5 对外分发** | 2.2 规划项 | SSE/WS 订阅、事件游标、快照接口 | 订阅方断线重连不丢事件；越权订阅被拒 |

## 7.2 每期的"完成"判据

统一四条，避免"做完了但不能用"：
1. 接口层：正例 + 反例（越权、只读、不存在）全部覆盖。
2. 数据层：跨库核对（本地库 vs 目标库）一致。
3. 界面层：真实浏览器跑通主流程截图留档。
4. 异常层：断网、上游异常响应、并发重入各演练一次。
