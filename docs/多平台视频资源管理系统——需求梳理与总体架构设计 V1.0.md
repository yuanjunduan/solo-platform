**一句话结论（先看这个）**

> 系统 = **一个资源中心**（组织/设备/通道，只有一份数据）+ **一张平台连接表**（每个外部平台只出现一次，带"收/发"两个方向能力）+ **两个过程中心**（同步中心负责把资源拉进来，共享中心负责把资源送出去）。
> 资源带"来源"标签，来源决定谁能改；共享关系与资源本体分离，每个上级平台有自己的目录视图和编码空间。
> 架构形态建议：**模块化单体**（一个可部署单元，内部按领域分包），不上微服务、不上消息中间件。

# 第一部分　项目需求

> 本章为需求方提供内容的完整结构化保留。原始条目编号（2.1 / 2.2 / 2.3 等）保留，便于逐条回溯。

## 1.1 项目背景

目前需要重新规划和设计一个全新的多平台视频资源管理系统。

在参考其他视频平台的过程中，发现部分平台在**组织管理、设备管理、通道管理、平台级联、资源共享**等方面，整体设计更加合理，用户操作也更加方便。

因此，本次**不要求沿用现有项目的设计方式，也不要求兼容现有架构**。这是一个全新的项目，允许从零设计。

需要结合实际业务需求、行业标准和成熟视频平台的设计经验，重新梳理业务模型、资源关系、功能边界和系统架构。

## 1.2 项目建设目标

核心目标（原文）：

- 组织、设备、通道统一管理。
- 支持本地资源自主维护。
- 支持海康、大华等外部平台资源接入。
- 支持多个平台之间的组织、设备、通道资源共享。
- 支持上级平台、下级平台级联。
- 支持资源通过 SSE / WebSocket 等方式对外提供。
- 支持视频播放、实时预览、录像回放等视频业务能力。
- 操作简单、业务清晰，方便用户理解和使用。
- 架构具有扩展性，后续可以接入更多厂商和平台。

设计方补充的可度量目标（供评审确认）：

| 目标 | 建议度量 |
|---|---|
| 统一管理 | 三类来源的组织/设备/通道，在同一个树、同一套查询接口中可见 |
| 操作简单 | 一次"资源共享"操作 ≤ 5 步，不跨超过 2 个页面 |
| 扩展性 | 新增一个厂商协议，只新增适配器实现，不改资源/共享核心代码 |
| 可追溯 | 任意一条通道可回答"来自哪、转给谁、什么时候同步的" |

## 1.3 核心业务概念

以下概念在需求中被反复使用，先在此统一命名，后续章节沿用。

| 概念 | 英文/代码名 | 定义 |
|---|---|---|
| 平台连接 | `platform` | 本平台与一个外部视频平台之间的一条接入关系（含认证、地址、协议、方向） |
| 平台角色 | `role` | 该连接相对本平台的角色：**下级平台**（资源从它流入本平台）/ **上级平台**（资源从本平台流向它） |
| 资源 | `resource` | 组织、设备、通道三类业务实体的统称 |
| 资源来源 | `source` | 资源的原始归属方：`NATIVE`（本平台）/ `平台ID`（某个外部平台） |
| 接入 | `onboard` | 配置连接、完成认证、建立可通信状态 |
| 同步 | `sync` | 从来源平台拉取或接收资源数据，写入资源中心 |
| 共享 | `share` | 声明"某些资源对某个上级平台可见" |
| 推送 | `publish` | 把共享关系转换成目标协议报文发送给上级平台 |
| 授权 | `grant` | 决定谁（人/平台）能看、能用哪些资源 |
| 转发 | `relay` | 把从 A 平台同步来的资源，共享给 B 平台 |

## 1.4 下级平台需求（原文 2.1）

### 1.4.1 外部资源接入

需要支持接入外部视频平台，例如：

- 海康威视平台。
- 大华平台。
- 后续其他符合行业规范的视频平台。

从外部平台获取：**组织信息、设备信息、通道信息**。

基本要求：

1. 外部平台的组织需要同步到本平台。
2. 外部平台的设备需要同步到本平台。
3. 外部平台的通道需要同步到本平台。
4. 组织具有父子关系，可以按照父子关系组装成组织目录树。
5. 通道必须归属于某个组织。
6. 同步过来的组织、设备、通道属于外部平台资源。

### 1.4.2 资源维护规则

通过外部平台同步过来的组织、设备、通道：

- 不允许在本平台直接新增。
- 不允许在本平台修改。
- 不允许在本平台删除。

这些资源以外部平台为数据来源，本平台主要负责**同步、展示、查询和使用**。

需要特别考虑外部平台发生资源变化时，本平台如何更新同步数据。例如：

- 外部新增组织。
- 外部新增设备。
- 外部新增通道。
- 外部组织名称发生变化。
- 外部设备或通道发生变化。
- 外部资源不再存在。

**注意（原文强调）**：禁止用户手动修改同步资源，不代表系统不能根据外部平台的变化更新本地同步数据。

### 1.4.3 对外资源共享（后续规划功能）

其他平台可以通过本平台获取指定下级平台的组织和通道资源。初步考虑：

- 支持指定下级平台。
- 支持查询该平台的组织目录树。
- 支持获取指定组织下的通道。
- 支持获取平台完整通道列表。
- 支持通过 SSE / WebSocket 获取资源变化。
- 支持资源同步状态管理。

需要考虑：

- 平台身份认证。
- 资源访问权限。
- 资源同步机制。
- 增量更新。
- 全量同步。
- 断线重连。
- 资源变更通知。

**SSE / WebSocket 的具体选择由架构分析后决定，不要为了使用技术而强行使用。**

## 1.5 上级平台需求（原文 2.2）

### 1.5.1 本地资源共享

本平台可以将自己的组织、设备、通道资源推送到上级视频平台，例如：本地组织、本地设备、本地通道。

这些资源可以共享到海康、大华等上级平台。

**注意**：本地组织、设备、通道的具体管理方式属于第 2.3 节，本节只定义它们在上级平台中的共享用途。

### 1.5.2 其他平台资源共享

除本地资源外，上级平台还需要支持将**其他平台的资源获取过来，再通过本平台共享给其他上级平台**。

```text
平台 A（海康）
    |
    | 获取组织、设备、通道
    v
本平台
    |
    | 资源统一管理、授权、转发
    |
    +------> 上级平台 B（海康）
    |
    +------> 上级平台 C（大华）
    |
    +------> 上级平台 D（其他厂商）
```

需要支持：

1. 从其他平台获取组织、设备、通道。
2. 将其他平台资源纳入本平台的资源体系。
3. 选择需要共享的资源。
4. 将资源推送到一个或多个上级平台。
5. 支持不同上级平台之间独立配置共享范围。
6. 支持不同厂商之间的资源协议适配。
7. 支持资源共享状态、同步状态、异常状态管理。

资源来源可能包括：

- 本地自建资源。
- 下级平台同步资源。
- 其他已经接入的平台资源。

需要考虑：**多级平台级联、资源来源追溯、重复资源处理、资源 ID 映射**等问题。

### 1.5.3 资源维护规则

上级平台获取或同步过来的组织、设备、通道：

- 不允许直接新增。
- 不允许直接修改。
- 不允许直接删除。

资源的原始数据归属于其来源平台。本平台负责**资源接入、展示、授权、共享和转发**。

### 1.5.4 级联平台管理

目前已经具备级联平台管理功能，主要用于维护多个上级平台信息，例如：

- 上级平台名称。
- 平台厂商。
- 平台类型。
- 平台地址。
- 认证信息。
- 平台连接状态。
- 级联状态。

本次重新设计时，需要重新评估级联平台管理的功能边界和架构，但**不需要因为重新设计而丢失现有的业务能力**。

需要支持：

- 一个本平台连接多个上级平台。
- 不同上级平台可以使用不同厂商协议。
- 不同上级平台拥有独立的资源共享配置。
- 各上级平台独立进行资源同步。
- 各上级平台独立管理同步状态和异常。

## 1.6 本地资源管理需求（原文 2.3）

### 1.6.1 本地资源管理

本地组织、设备、通道支持：新增、修改、删除、查询、组织树管理、设备管理、通道管理。

### 1.6.2 资源关系

- **组织**：支持父子级关系；支持多级组织目录树；组织可以管理多个设备。
- **设备**：一个组织可以包含多个设备；设备可以拥有多个通道。
- **通道**：必须归属于一个组织；支持设备与通道之间的关联；支持通道状态管理。

需要分析组织、设备、通道之间的合理数据模型。

### 1.6.3 本地资源的其他用途

本地资源除了自主管理，还可以：

1. 共享给一个或多个上级平台。
2. 作为其他平台资源共享的组成部分。
3. 用于本平台的视频播放业务。
4. 用于实时预览。
5. 用于录像回放。
6. 用于后续其他视频业务。

**本地资源需要具备完整的视频业务能力，不能仅仅作为组织、设备、通道的静态数据。**

## 1.7 多平台资源共享需求（综合 2.2 + 2.3）

| 需求点 | 说明 |
|---|---|
| 多上级并行 | 一个本平台连接多个上级，各自独立配置共享范围、独立同步、独立异常 |
| 跨厂商 | 上级可能是海康、大华或其他厂商，协议与报文格式不同 |
| 转发 | A → 本平台 → B/C/D，允许再往下级联 |
| 来源追溯 | 任意资源可回答"原始归属 + 经过哪些平台" |
| 重复处理 | 同一物理资源经不同路径进入时，不产生重复目录项 |
| ID 映射 | 本平台编码 ↔ 各上级暴露编码，双向可解析 |
| 撤销 | 共享可撤回，且撤回后上级侧同步移除 |
| 状态 | 共享状态、同步状态、异常状态都要可见 |

## 1.8 视频业务需求

| 能力 | 要求 |
|---|---|
| 实时预览 | 本地资源、外部同步资源都能通过统一接口播放 |
| 录像回放 | 同上，支持按时间检索、按时间段回放 |
| 设备控制 | 云台控制、预置位（本地与外部资源都要支持，能力取决于来源） |
| 通道状态 | 在线/离线/录像中；状态变化要能反映到列表与目录树 |
| 播放记录 | 可查询谁在什么时候看了哪路视频（审计要求，建议纳入） |
| 播放会话管理 | 同一路视频多人观看应复用同一路流，不重复向上游拉流 |

# 第二部分　AI 对需求的理解

> 本章不引入技术方案，只把"业务到底是什么"讲清楚。第三部分的每个设计决策都应能回溯到本章的某条结论。

## 2.1 业务角色分析

本平台在整条链路上处于**中间汇聚层**，同时扮演三种角色：

| 角色 | 对谁 | 本平台做什么 | 本平台不做什么 |
|---|---|---|---|
| **资源持有者** | 本地 | 自建、自维护组织/设备/通道，承载视频业务 | — |
| **资源消费方**（下级关系的上游） | 海康/大华等下级平台 | 注册过去、订阅/查询目录、按需取流 | 不修改对方数据、不接管对方设备 |
| **资源提供方**（上级关系的下游） | 海康/大华等上级平台 | 提供目录、接受点播/回放/云台、上报状态 | 不反向索取上级资源、不修改上级配置 |

三种角色**不是三种系统**，而是同一个资源中心对外呈现的三种视图。这决定了：

- 不需要为"下级"和"上级"各建一套组织表/设备表/通道表（那会产生三份数据、三套同步逻辑）。
- 需要为"下级"和"上级"各建一套**关系表**（同步关系 / 共享关系），因为关系才是随方向变化的。

## 2.2 平台之间的关系

### 2.2.1 四种关系形态

| 形态 | 方向 | 典型场景 | 数据流向 |
|---|---|---|---|
| 只收 | 对方 → 本平台 | 本平台汇聚海康下级平台 | 目录入、流按需拉 |
| 只发 | 本平台 → 对方 | 本平台向大华上级平台共享 | 目录出、流按需推/拉 |
| 双向 | 互相 | 两个平级平台互为上下级（少见但标准允许） | 两个方向都有 |
| 互联（非级联） | 双向 API | 通过 SSE/HTTP 自定义集成 | 只走业务接口，不走视频协议 |

**结论（回答 B1/B2/B3）**：

1. 上/下级**不应**做成两套独立模块，应统一为 **平台连接（Platform Connection）**，方向作为连接的属性（`accept_inbound` / `push_outbound` 两个能力位）。
2. 一个外部平台**可以**同时是"资源提供方"和"资源接收方"。国标 SIP 栈本身就是双向的，技术上没有障碍。
3. 但要允许"同一物理平台配成两条连接"（分别配认证与协议参数），因为厂商侧的两套接口常常是不同端口/不同账号。

### 2.2.2 与"循环同步"的关系

允许双向连接，就必须防环。判断环需要三个信息：**来源链、跳数、平台身份**，缺一不可（详见 3.10.2）。

## 2.3 资源之间的关系（关键：三棵树，不是一棵）

这是全篇最重要的认知。系统里同时存在**三类目录树**：

```
树①  本地组织树           ← 本平台自建，可编辑
      总部 / 园区A / 一号楼

树②  下级平台自带组织树     ← 每个下级平台各一棵，只读
      海康A → (海康A的组织) 
      大华B → (大华B的组织)

树③  面向上级平台的目录树   ← 每个上级平台各一棵，由本平台生成
      给海康上级看的：(重点单位 / 一号楼) / 通道...
      给大华上级看的：(园区) / 通道...
```

**它们不能合成一棵树**，原因有三：

| 若强行合并 | 后果 |
|---|---|
| 把海康的组织挂进本地组织树 | 本地组织树将出现"不能改、不能删、删了还会回来"的节点，用户无法理解 |
| 多个下级平台的组织同根 | 编码不同域，同级重名（都叫"园区"）无法区分 |
| 上级看到的树 = 本地树 | 无法实现"给 A 平台看重点单位、给 B 平台看全量"，违背 C6 |

所以正确的模型是：

> **树是"视图"，不是"数据的容器"。**
> 资源数据只有一份（组织/设备/通道各一张表），三棵树都是对这份数据的不同"分组方式"。

具体落地：

- 树① = `res_org WHERE source=NATIVE`，父子关系在表内。
- 树② = `res_org WHERE source=平台X`，父子关系同样是表内 `parent_id`，只是一次查一个平台。
- 树③ = **独立的映射表**（`out_group`），不引用 `res_org` 的主键，只引用"资源标识"。它是"给谁看"的投影。

### 2.3.1 组织 / 设备 / 通道的层级

```
组织 (1) ───< 设备 (n) ───< 通道 (n)
   │                          │
   └──────── 通道必须归属组织 ──┘   （组织是通道的"位置"，设备是通道的"载体"）
```

需求 C4 说"通道必须归属于某个组织"。这里有两条**同时成立**的链路：

| 链路 | 字段 | 用途 |
|---|---|---|
| 通道 → 组织（位置） | `org_id` / `org_path` | 目录树展示、按组织筛选、共享选范围、权限控制 |
| 通道 → 设备（载体） | `device_id` | 播放取流（设备是信令目标）、设备删除时级联 |

两条都必须有。**只存 org_id 不够**（无法取流），**只存 device_id 也不够**（设备可能跨组织，且组织是业务归属）。

另外：下级平台目录里存在"分组行"（GB28181 的 215 业务分组 / 216 虚拟组织），它们**不是设备**，但必须能承载通道。设计上把它们放在通道表里以 `kind=GROUP` 表示（或独立一张 `res_group`），再让通道的 `org_id` 指向它。本设计采用**独立 `res_group` 表**，理由是设备表/通道表都挂 `kind` 会污染主表语义（详见 3.6.1）。

## 2.4 资源来源和数据归属

### 2.4.1 三种来源，两种归属

| 来源类型 | 代码 | 数据归属 | 用户可写 | 系统可写 |
|---|---|---|---|---|
| 本平台自建 | `NATIVE` | 本平台 | 是（完整 CRUD） | 是 |
| 下级平台同步 | `INBOUND`（附 `source_platform_id`） | 来源平台 | **否** | 是（同步任务） |
| 已失效/已删除 | 保留原来源 + `status` | 原归属不变 | 否 | 是（清理任务） |

### 2.4.2 一个重要澄清：**"转发资源"不是第四种来源**

原始需求（11.3 的表格）把"转发资源"列为一种独立资源类型。设计方建议调整表述：

> **转发是一个"出站动作"，不是一个"来源类型"。**
> 从 A 平台同步来的通道，来源永远是 A；它被共享给 B 平台，产生的是"B 的共享关系"，不改变资源来源。

理由：
1. 若把转发资源当独立来源，同一条通道会存在两份数据（A 的镜像 + 转发的副本），同步、状态、删除都要做双份，且两边会漂移。
2. 资源追溯会断链——无法回答"这条到底是 A 的还是 B 的"。
3. 共享范围调整时，需要同步两份数据，出 bug 的概率翻倍。

因此全系统的来源判定只有一条规则：

```
资源归属 = 该资源第一次被创建时的平台连接
（本地创建 → NATIVE；某平台同步进来 → 该平台）
此后无论被共享给多少个上级、被多少下游消费，归属都不变
```

## 2.5 资源同步与共享的区别（需求 3.3 要求拆分）

七个概念必须分开，混用会导致"同步一个平台=共享一个平台"这类错误实现。

| 概念 | 方向 | 触发者 | 改什么数据 | 失败后果 | 用户是否可见 |
|---|---|---|---|---|---|
| **接入** Onboard | 建连 | 管理员配置 | `platform` + `credential` | 一直连不上，重试 | 可见（平台状态） |
| **同步** Sync | 入 | 定时/手动/通知 | 资源表（`res_*`） | 目录不全，重试/对账 | 可见（同步中心） |
| **管理** Manage | 内 | 用户 | 资源表（仅 NATIVE） | 校验拦截 | 可见（本地维护） |
| **授权** Grant | 内 | 管理员 | 权限表 | 越权被拒 | 可见（角色/范围） |
| **共享** Share | 声明 | 用户 | `out_share` | 无即时影响，等待推送 | 可见（共享编排） |
| **推送** Publish | 出 | 共享变更/资源变更 | `outbox` → 外部平台 | 上级看不到，积压 | 可见（推送记录） |
| **状态同步** Status | 双向 | 心跳/通知 | `status` 字段 | 显示状态错误 | 可见（列表圆点） |

**用户界面只暴露 3 个主动动作**：接入平台、发起同步、设置共享。授权与推送是系统内部过程，只在必要时提示状态。

## 2.6 业务边界

明确"我们不做什么"，比"我们做什么"更能防止架构跑偏：

| 边界 | 说明 |
|---|---|
| 不写回上游 | 本平台不对下级/上级平台做资源修改，只读 + 按需取流 |
| 不订阅上级目录 | 上级只接收本平台推送的目录，不反向拉取（避免环） |
| 不跨路径物理合并 | 同一物理设备经两条路径进入时保留两条记录；按全局身份（`origin_platform_id + origin_code`）**自动建立关联**（`canonical_id`），但**不做物理合并**——合并会丢失来源链、共享关系与"一条失效另一条仍可用"的语义 |
| 不负责修复上游不可播 | 来源平台无流、编码不支持时，如实报错并给出原因，不做本地转码兜底（首版） |
| 不做资源内容编辑 | 不提供图片、点位、备注之外的内容加工（首版） |
| 不做多租户隔离 | 首版单租户，但表结构预留 `tenant_id`（见 2.7-8） |

## 2.7 现有需求中需要优化的地方

以下 8 条是设计方认为需要与需求方对齐的调整，**不改变业务含义**，只优化表述与边界。

| # | 问题 | 建议 | 影响 |
|---|---|---|---|
| 1 | "上级平台/下级平台"既是菜单名又是角色名，容易把一个平台当两个东西 | 底层统一为"平台连接 + 方向能力位"；**界面**仍可保留"下级/上级"作为筛选标签（用户认知友好），但数据只有一条 | 避免重复建平台、重复认证 |
| 2 | "同步资源不能删除"缺少"系统可以删"的明确机制 | 区分**失效（STALE）/ 下线（OFFLINE）/ 删除（REMOVED）** 三态；用户不能操作，系统按同步结果与宽限期操作，且留墓碑 | 否则上游删了资源，本地永久残留 |
| 3 | "通道必须属于组织"与协议现实冲突（部分平台不推组织） | 强制兜底：自动建 `[未分类]` 组织并标记"上游未提供组织"，不允许游离 | 保证 C4 可落地，且问题可见 |
| 4 | 转发的授权问题未定义 | 建议：转发不要求原平台授权（本平台是汇聚点），但共享记录必须留存来源，供审计 | 若不明确，后期会被追问"凭什么转我的资源" |
| 5 | "重复资源处理"无判定标准 | 两级判定：**存储唯一性**用（来源平台 + 原始编码），**跨路径同一性**用（最上游平台 + 原始编码） | 两个平台的相同测试码可并存；同一设备经两条路径进来可自动识别为同一实体 |
| 6 | SSE/WS 的受众未明确 | 判定为**自定义集成方/自有系统**，不是海康大华平台（它们只认国标/私有协议） | 避免做出"厂商用不了"的接口 |
| 7 | 视频能力与资源模型耦合风险 | 资源只存"取流路径线索"，不存"如何取流"；取流由媒体层按来源解析 | 保证 C9 |
| 8 | 多租户未在正文出现，但 4.6 提到 | 首版不做，表结构预留 `tenant_id`（默认 1） | 后期加不改表 |

另外两条表述建议（不改设计，只改叫法）：

- 用 **"汇聚"** 代替"下级资源管理"，用 **"共享"** 代替"上级资源共享"，让菜单脱离方向词，用户不需要先理解"谁是上级"。
- 用 **"来源"** 而不是"平台类型"，因为同一平台可能既提供又接收。

# 第三部分　推荐总体架构

## 3.1 架构设计思路

六条思路，每条都对应第一部分的一条约束。

| # | 思路 | 对应约束 | 反例（要避免的做法） |
|---|---|---|---|
| **P1** | 一个资源中心 + 两个过程中心 + 一张连接表 | C1/C2、原则 6 | 按"下级/上级"各建一套组织/设备/通道管理 |
| **P2** | 资源与关系彻底分离 | C6、原则 9/12 | 为每个上级复制一份通道数据，或把 exposedCode 写在通道表上 |
| **P3** | 树是视图，不是容器 | C5、C6 | 把下级组织挂进本地组织树，用 `type` 字段区分"本地节点/镜像节点" |
| **P4** | 协议隔离在适配器边界，同步协议与播放协议分开 | 原则 8/13 | 在 Service 里直接拼 GB28181 XML；用取流代码判断资源来源 |
| **P5** | 一致性靠"事实 + 对账"，不靠"事件必达" | C3、原则 11 | 资源改完直接发 MESSAGE，失败就丢；只靠内存重试 |
| **P6** | 模块化单体（一个部署单元，包边界即未来拆分边界） | C10、原则 14/15 | 一上来拆 8 个微服务 + Kafka |

### 3.1.1 为什么是"模块化单体"而不是微服务

| 判断依据 | 结论 |
|---|---|
| 业务规模 | 单平台典型量级：组织 1k~1w、设备 1w~10w、通道 10w~100w；单库可承载 |
| 一致性要求 | 资源写入与出站事件必须同事务（Outbox），跨服务会退化为最终一致 + 分布式事务 |
| 团队规模 | 初期 3~8 人，微服务的运维成本会吃掉全部产能 |
| 拆分时机 | 当"适配器数量 > 5 且各自依赖冲突"或"媒体转码 CPU 打满"时再拆；两者现在都不成立 |

**单体的纪律（比"上不上微服务"更重要）**：

1. 模块间**只允许**通过 `xxxApi`（接口）+ 领域事件通信，禁止 import 其它模块的 Mapper / Entity。
2. 每个模块独占自己的表前缀，禁止跨模块 JOIN。
3. 定时任务归属模块，统一注册到调度中心（一个 `@Scheduled` 入口分发，避免散落）。
4. 模块依赖单向：`adapter → resource`，`sync → resource + adapter`，`share → resource`，`publish → share + adapter`；反向依赖一律用事件。

## 3.4 核心模块职责

### 3.4.1 模块划分（回答 B1/B2）

| 模块 | 输入 | 输出 | 依赖 | 明确不负责 |
|---|---|---|---|---|
| **platform** 平台连接 | 平台配置、认证信息、心跳/注册事件 | 连接状态、能力位、凭证 | 无（最底层） | 不存任何资源数据 |
| **resource** 资源中心 | 资源写入请求（本地 CRUD / 同步写入） | 资源查询、树查询、统一检索 | platform | 不判断"该不该推给谁" |
| **sync** 同步中心 | 同步请求（定时/手动/通知触发） | 资源写入指令、同步任务与明细 | platform、resource、adapter.inbound | 不直接发目录给上级 |
| **share** 共享中心 | 共享配置变更 | 共享关系、虚拟组织树、编码映射 | resource、platform | 不发报文 |
| **publish** 推送中心 | 资源变更事件、共享变更事件 | 出站报文投递、推送状态、对账结果 | share、platform、adapter.outbound | 不决定"共享什么" |
| **media** 视频业务 | 播放/回放/控制请求 | 播放会话、媒体地址、控制结果 | resource、platform、adapter.media | 不管资源归属 |
| **dispatch** 对外分发 | 事件 + 订阅关系 | SSE/WS 推送 | resource（订阅事件） | 不做协议级联 |

**为什么 share 与 publish 分开**：共享是"声明"（数据库里配置），推送是"投递"（网络动作）。合并后会出现"配置页面卡住等网络"的问题，且无法独立重试。分开后，共享配置 100% 成功即返回，推送异步补齐并可见。

### 3.4.2 方向能力位（回答 B3）

```sql
-- platform 表中的两个能力位
accept_inbound   TINYINT  -- 1=允许该平台向本平台推目录（它是我的下级）
push_outbound    TINYINT  -- 1=允许本平台向该平台推目录（它是我的上级）
```

四种组合都合法：`10` 只收、`01` 只发、`11` 双向、`00` 仅登记（用于只做认证或仅观测）。

### 3.4.3 模块间的关键事件

| 事件 | 发布方 | 订阅方 | 用途 |
|---|---|---|---|
| `ResourceCreated/Changed/Removed` | resource | share、publish、dispatch | 资源变了 → 找到受影响的共享 → 写 Outbox；同时推 SSE |
| `ShareChanged` | share | publish | 共享范围变了 → 生成 ADD/DELETE 事件 |
| `PlatformOnline/Offline` | platform | sync、publish | 上线触发补同步；离线暂停推送队列 |
| `SyncCompleted` | sync | share（可选） | 同步完成 → 提示"新资源可共享" |

## 3.5 核心数据模型

### 3.5.1 设计决策：4 张资源表（回答 A1）

需求方特别提醒："不要简单把所有资源放同一张表，也不要为了区分来源设计大量重复表。"

三种方案对比：

| 方案 | 表数量 | 优点 | 致命缺点 | 结论 |
|---|---|---|---|---|
| 全部资源一张大表 | 1 | 查询简单 | 组织/设备/通道字段差异 > 60%，大量 NULL，索引无法有效利用；一条 SQL 里全是 `CASE WHEN type=` | ❌ |
| 按来源 × 类型拆表 | 3×4 = 12 | 物理隔离彻底 | 跨来源统一查询要 UNION 12 张表；每加一种来源要加 4 张表；同步/共享代码要写 3 套 | ❌ |
| **按类型拆表 + 来源作列** | **4（org/device/channel/group）** | 每张表字段紧凑、索引有效；跨来源查询天然一条 SQL；加来源不改表 | 来源隔离靠条件而非物理 | ✅ **采用** |

> 一句话：**"来源"是行的一个属性，不是表的维度。** 表的维度是"资源类型"，因为类型决定字段。

### 3.5.5 为什么这样设计（逐条回答 A2~A5）

| 问题 | 回答 | 理由 |
|---|---|---|
| A2 是否需要独立的"资源来源管理"表 | **不需要独立表，用 `platform` + 3 个字段** | 来源就是平台连接，已有 `platform` 表；再建 `resource_source` 表是同一数据两份 |
| A3 是否需要来源 ID、原始平台 ID | **需要**：`source_type` + `source_platform_id` + `origin_chain` | 前两个定归属，第三个定链路（追溯与防环） |
| A4 是否需要资源映射表 | **需要，仅出站需要**（`out_code_map`）；入站不需要 | 入站保留原始码即可（各来源独立命名空间）；出站要给每个上级一套暴露码 |
| A5 是否需要独立共享关系表 | **必须独立** | 资源一份、共享 N 份；写在资源表上会导致"每加一个上级就改资源表" |

## 3.6 资源统一管理方案

### 3.6.1 一套模型，四种资源类型

资源中心只有 4 张主表：`res_org` / `res_group` / `res_device` / `res_channel`。**来源不是表，是列**。

为什么分组要独立成表而不是塞进通道表（很多平台的做法）：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 分组塞进 `res_channel`（`kind=GROUP`） | 少一张表 | 通道表要承载"非通道"数据：`org_path`、`device_id`、`capability` 全为空；按通道统计要处处加 `kind=0`；外键语义混乱 | ❌ |
| 分组独立 `res_group` | 语义干净、统计简单、可单独建索引 | 多一张表 | ✅ |

`res_group` 与 `res_org` 结构高度相似（都是树），但**语义不同**：`res_group` 是"上游目录里的分类节点"，只在入站镜像里出现；`res_org` 是"组织"。合并会让"组织"这个概念被污染（组织有归属、有人员、有权限；分组只是分类）。

### 3.6.2 来源字段设计（不用枚举表）

```sql
source_type         VARCHAR(16)  -- NATIVE / INBOUND
source_platform_id  BIGINT       -- 直接来源平台：0 = 本地；否则 platform.id（决定"谁能改"）
origin_chain        VARCHAR(128) -- 平台ID链，如 "5,9"：先经平台5，再经平台9（防环用）
hop_count           SMALLINT     -- 跳数
origin_platform_id  BIGINT       -- 最上游平台：0 = 本地或未知
origin_code         VARCHAR(64)  -- 最上游平台上的原始编码
code_chain          JSON         -- 全链码：[{"p":5,"c":"..."},{"p":9,"c":"..."}]（展示/核对用）
canonical_id        BIGINT       -- 同一实体组主记录 id，0 = 自身为组主（去重用）
```

**两组字段解决两个不同问题，不能合并：**

| 字段组 | 回答的问题 | 用于 |
|---|---|---|
| `source_platform_id` + `code` | **这条数据是谁给我的**（决定写权限、同步归属、共享来源） | 只读校验、同步覆盖、共享配置 |
| `origin_platform_id` + `origin_code` | **这条数据最初是谁的**（跨路径识别同一物理资源） | 重复检测、来源追溯、跨级映射 |
| `origin_chain` + `hop_count` | **经过了哪些平台、多深** | 防环、级联深度限制 |
| `canonical_id` | **它和谁是同一台设备** | 列表归并展示、播放选路 |

**为什么"最上游码"才是全局身份**：

- A 的通道码 `X` 只在 A 的命名空间内唯一；B 把 A 的资源重编号成 `Y` 后，`Y` 只在 B 的命名空间内唯一。
- 如果本平台记录的是"上一跳码"（B 给的 `Y`），它无法与"A→本平台"直接拿到的 `X` 比对。
- 只有把链路顶端的 `(A, X)` 保留下来，两条路径才有共同的比对键。
- 所以：**`origin_platform_id + origin_code` 才是"这台设备是谁"，`code` 只是"这次是谁告诉我的"**。

**码链的填充规则（入站）**：

```
若能解析上游携带的码链：[..., {B, Y}]        → 继承并把直接来源追加到尾部
若不能解析（上游未携带）：[ {直接来源, code} ]  → origin 退化为直接来源，链长 1
```

**携带规则（出站，本平台可控）**：本平台向上级推目录时，**必须**在目录项扩展字段里带 `OriginPlatformId` + `OriginCode`（见 3.9.3）。这样下游平台（C）也能拿到全局身份，整条链才闭合。

> 这是"我们控制得了的部分"：对自己出站强制携带，对入站尽力解析。两者都做到，跨路径识别才能从"靠猜"变成"靠数据"。

### 3.6.3 来源追溯（回答 A9）

四种追溯视角，分别用不同的字段组：

| 视角 | 查询 | 输出 |
|---|---|---|
| 这条资源从哪来 | `SELECT source_platform_id, origin_platform_id, origin_code, code_chain FROM res_channel WHERE id=?` | `来自 大华B（最上游：海康A / 34020000001310000001）` |
| 全链路每一跳的码 | 读 `code_chain` | `A:340200...001 → B:340201...087 → 本平台:340299...042` |
| 某平台贡献了多少资源 | `WHERE source_platform_id=? AND status<>'REMOVED'` | 平台资源统计 |
| 这条资源流向了谁 | `SELECT platform_id FROM out_share WHERE ref_code=? AND ref_source_platform_id=?` | 已共享给 A、C 两个上级 |

**追溯能力分三档，界面必须如实展示当前处在哪一档**（不允许"看起来完整"）：

| 档位 | 条件 | 界面展示 |
|---|---|---|
| **A 档：全链** | 上游携带了完整码链 | `来源：大华B → 海康A → 本平台`（可展开看每跳编码） |
| **B 档：直达上游** | 上游仅提供直接来源码（最常见） | `来源：大华B（最上游未知）` |
| **C 档：仅本平台** | 本地资源 | `来源：本地维护` |

**生成规则**：入站写入时按 3.6.2 的填充规则处理；`origin_chain` 用于防环，`code_chain` 用于展示与人工核对，两者**分开存**（链可能断，但平台链只要有直接来源就一定非空）。

### 3.6.4 跨平台统一查询（回答 A8）

因为来源是列，所有列表查询都是单表 + 条件，**不需要 UNION**：

```sql
-- 全部来源的通道，按组织子树筛选
SELECT * FROM res_channel
WHERE status <> 'REMOVED'
  AND org_path LIKE CONCAT('/1/12/', '%')     -- 组织子树
  AND (source_type = 'NATIVE' OR source_platform_id IN (5, 9))  -- 来源过滤（可选）
ORDER BY online_status DESC, code
LIMIT 20 OFFSET 0;
```

左树同理：`res_org` 一次查出某来源的全部节点，用 `parent_id` 在内存组树（1 万节点级别完全可接受），或按 `parent_id` 逐层懒加载（10 万级必须懒加载）。

**性能基线**：`res_channel` 100 万行时，`idx_org_path` + `idx_src` 足以支撑 200ms 内的分页查询；超过 300 万行再按 `source_platform_id` 做分区。

### 3.6.5 只读保障（回答 A10）

四层收口，加一条审计：

| 层 | 措施 | 失效场景 |
|---|---|---|
| API 层 | 写接口带 `@ResourceWrite` 注解，切面校验资源 `source_type=NATIVE` | 新接口忘记加注解 → 由第二层兜底 |
| 领域层 | `ResourceService.assertWritable(id)`：任何 UPDATE 前强制校验 | 直接调 Mapper → 由代码评审 + 架构测试兜底 |
| 持久层 | MyBatis 拦截器：`UPDATE res_* SET ...` 若未带 `source_type='NATIVE'` 条件则告警（开发环境直接抛错） | 原生 SQL → 由 DBA 权限兜底 |
| 数据库 | 业务账号对 `res_*` 无 DELETE 权限，只允许软删（`UPDATE status`） | — |
| 审计 | 所有对 `res_*` 的写操作记录操作人与来源（用户/同步任务） | — |

**关键细节**：`INBOUND` 资源允许系统改的字段集合要显式白名单（`name`、`online_status`、`capability`、`status`），不允许改 `code`、`parent_id`、`source_platform_id`——否则同步一次就可能"改掉别人的身份"。

### 3.6.6 入站资源的主键必须稳定（硬约束）

一条铁律：**入站资源永远"原地更新"，永不"删除重建"**。

| 项 | 规定 |
|---|---|
| 定位 | 按唯一键 `(source_type, source_platform_id, code)` 定位唯一行，UPDATE 该行 |
| 禁止 | `DELETE FROM res_* WHERE source_platform_id = ?` 之后再全量 INSERT |
| 原因 | `res.id` 被 `out_share`、`out_code_map`、`canonical_id`、播放会话、审计记录引用；id 一变，这些关系全部悬空或错指 |
| 唯一例外 | 首次接入（本地无该平台任何数据）时的初始 INSERT，不涉及重建 |

**为什么单独立一条**：全量同步最直觉的写法是"先清空该平台的镜像，再全量插入"。功能上看起来正确——同步完成后数据确实一致。但它有三个后果：

1. 共享关系（`out_share` 存的是资源 id）在"已删未插"的窗口内指空，此时上级来拉目录会拿到不完整结果；
2. `out_code_map` 里的暴露码失去宿主，重新插入后要么撞码、要么换码，上级侧已经拿到的编码全部失效；
3. 崩溃恰好发生在删完未插之间，该平台镜像直接归零，且没有中间态可回滚。

**如果主键规则本身会导致重建**（例如编码由"域段 + 自增序号"生成，见 3.9.3），则必须补一层"ID 复用判定"：

```
对新拉取到的资源 R（业务键 = source_platform_id + code）：
    本地已有同业务键的行 → 复用其 id，只更新可变字段
    本地无同业务键的行   → 新分配 id
    业务键变了但按"父路径 + 编码规则"可判定是同一实体 → 复用 id，并记录一次搬迁
```

这是外部实践里最容易漏的一条：靠"全删重插 + 组织 ID 复用判定"两件事拼起来才能保住关联，代价是多了一次修补。正确的做法是**根本不做全删**，让问题不发生。

## 3.7 平台接入与协议适配方案

### 3.7.1 三层协议必须分开（需求 3.4 的关键提醒）

需求方明确指出："**组织、设备、通道资源同步协议，与视频播放、信令控制协议不是同一层面**。"

| 层面 | 协议 | 谁用 | 适配器 |
|---|---|---|---|
| **资源同步协议** | GB28181 Catalog/Subscribe、ONVIF Device/Media、厂商私有目录 API | sync 模块 | `InboundAdapter` |
| **资源共享协议** | GB28181 Catalog 响应/Notify、厂商私有推送 API | publish 模块 | `OutboundAdapter` |
| **媒体协议** | SIP INVITE + RTP/PS、RTSP、厂商 SDK | media 模块 | `MediaAdapter` |

**同一平台可能三种协议都不同**：例如海康下级平台用 GB28181 同步目录，但取流走 RTSP 或 SDK。因此 `platform` 表里 `protocol` 字段不能只有一个，应为：

```sql
sync_protocol     VARCHAR(32)  -- 目录同步用什么
publish_protocol  VARCHAR(32)  -- 共享推送用什么
media_protocol    VARCHAR(32)  -- 取流用什么
```

### 3.7.2 统一中间模型

适配器与领域层之间只传**与协议无关**的结构：

```java
// 目录项（入站/出站共用）
class CatalogItem {
    String code;              // 对端给的编码（入站=直接来源码；出站=暴露码）
    String parentCode;
    ItemType type;            // ORG / GROUP_BUSINESS / GROUP_VIRTUAL / DEVICE / CHANNEL
    String name;
    String status;            // ON / OFF

    // ---- 全局身份（出站必须带，入站尽力解析）----
    Long   originPlatformId;  // 最上游平台（对端视角的标识，通常是其国标码/平台编码）
    String originCode;        // 最上游编码；为空表示对端未提供
    List<CodeHop> codeChain;  // 码链（可选），用于上游/下游完整追溯
    Integer hopCount;         // 对端告知的跳数

    Map<String,String> attrs; // 协议特有字段（厂商/型号/IP/云台能力…）
}

class CodeHop { Long platformId; String code; }  // 一跳：哪家的哪个码

// 取流意图
class MediaRoute {
    MediaProtocol protocol;   // SIP_GB28181 / RTSP / SDK
    String targetCode;        // 对端使用的编码（可能是暴露码）
    String streamProfile;     // 主/子码流
    Map<String,String> params;// 端口、SSRC、传输模式等
}

// 控制指令
class PtzCommand { String code; Command cmd; int speed; ... }
```

领域层**只认这三个模型**，永远不会出现 `SipMessage`、`ONVIF Device` 这类协议对象。

### 3.7.3 适配器 SPI

```java
interface InboundAdapter {
    String protocol();                                    // "SIP_GB28181"
    ConnectResult connect(PlatformConn conn);             // 注册/登录
    List<CatalogItem> fetchAll(PlatformConn conn, Progress p);      // 全量
    void subscribe(PlatformConn conn, CatalogListener l);            // 增量通知
    void disconnect(PlatformConn conn);
}

interface OutboundAdapter {
    String protocol();
    PublishResult publish(PlatformConn conn, List<CatalogItem> items); // 目录推送
    PublishResult revoke(PlatformConn conn, List<String> codes);       // 撤销共享
}

interface MediaAdapter {
    String protocol();
    PlayHandle invite(PlatformConn conn, MediaRoute route);            // 实时
    PlayHandle playback(PlatformConn conn, MediaRoute route, TimeRange t);
    void ptz(PlatformConn conn, PtzCommand cmd);
    void bye(PlayHandle h);
}
```

**新增厂商只需**：实现一个或多个接口 + 在 `platform` 表登记 `protocol` 值 + 注册到工厂。资源、共享、推送、播放的核心代码**零改动**（对应原则 8）。

### 3.7.4 编码差异处理（回答 A7）

| 差异 | 处理方式 |
|---|---|
| GB28181：20 位数字，`前10位域 + 3位类型 + 7位序号` | 原样保留；类型段可用于识别"平台/设备/通道/分组" |
| ONVIF：无国标码，用 `token` 或 URI | **本地生成虚拟编码**（按平台分配的号段），原始 URI 存在 `media_hint`/`attrs` |
| 厂商私有：数字 ID 或 GUID | 同上：本地编码 + `source_code` 原始值双向可查 |
| 多来源同码 | 唯一键 `(source_type, source_platform_id, code)`，天然隔离，不需要改码 |
| 出站同码冲突 | `out_code_map` 分配暴露码；分配后**不随资源改名/移动而变化** |

**核心规则**：**入站不改码，出站才重编号**。这样入站永远可回溯到上游；出站每平台独立，互不影响。

## 3.8 资源同步方案

### 3.8.1 同步策略矩阵

| 策略 | 触发 | 适用 | 实现要点 |
|---|---|---|---|
| 全量 | 首次接入 / 手动 / 定时兜底 / 对账发现偏差 | 初始接入、结构性变化 | staging 表 + 事务合并 + 差异计算 |
| 增量（通知） | 上游 Notify/订阅推送 | 日常变更 | 单条 upsert，幂等 |
| 增量（轮询） | 定时拉取变更列表 | 上游不支持订阅 | 按 `update_time` 或版本号拉取 |
| 手动 | 用户点"同步" | 排障、临时刷新 | 与全量同一链路，可取消 |

`platform.sync_policy` 四值：`MANUAL` / `SCHEDULED` / `NOTIFY` / `BOTH`（定时 + 通知兜底）。

**建议默认**：`BOTH`。只依赖通知的平台，一旦上游不发通知就永久失联；只依赖定时的平台，变更延迟不可控。

### 3.8.2 全量同步算法（关键：不产生半截数据）

#### 一轮同步的三段会话

无论是上级主动推、还是本平台向上游拉，一轮全量都按三段推进：

| 阶段 | 谁发起 | 本平台做什么 | 返回 |
|---|---|---|---|
| `start` | 上级 / 调度器 | 建 `sync_task(RUNNING)`，登记 `task_sn`、平台、预计条数 | 接受 / 拒绝（平台忙） |
| `synching`（可多次） | 上游分批推 / 本平台分批拉 | 每批写 staging，累计进度 | **每批独立 ACK** |
| `finish` | 上级 / 本平台 | 单事务合并、计算差异、广播事件、写轮次台账 | 本轮摘要 |

三条关键语义：

1. **ACK 是批级的，不是轮级的**。某批失败只让对端重发这一批，不重跑整个全量。百万级场景下这一点决定"失败一次要不要等一小时"。
2. **超时按"无进展"判定，不按总时长**。连续 N 秒（默认 75s，可配）没有收到新批次即判定本轮超时并清理会话；只要批次还在来，跑多久都不算超时。
3. **失败后进入冷却窗口**。失败轮收尾后的一段时间（默认 `超时 + 10s`）内拒绝再次触发，把"本端已空闲、对端仍在等它自己的超时"这段空窗补齐。冷却存 Redis（键带 TTL，值存失败时间戳），**不放进程内变量**——重启和多实例都不能丢。

> 第 3 条看着小，但没有它，运维在失败后立刻点"重新同步"就会与上一轮尚未熄灭的会话撞车，表现为"偶尔提示平台忙、偶尔数据对不上"，且难以复现。

#### 拉取与生效分离（staging）

```
1. 创建 sync_task(PENDING) → RUNNING
2. 逐页拉取 Catalog（每页 200~500），写入暂存表 sync_staging（加 task_id）
   每页更新 task.progress，支持取消（取消则DROP暂存，资源不动）
3. 全部拉完 → 进入合并阶段（单事务）：
   a. 校验：通道的 org_code 是否存在于本次拉取的组织集合
      - 缺失 → 归入 [未分类] 组织（自动创建，标记原因）
   b. UPSERT 组织 / 分组 / 设备 / 通道（按业务键）
   c. 计算消失集合：本次未出现 且 上次存在 且 状态=ACTIVE
      → 置 STALE，进入宽限期（默认 24h）
   d. 计算新增集合 → 发布 ResourceCreated 事件
   e. 更新 platform_catalog_ver（本次快照指纹 + 时间）
4. sync_task → SUCCESS，记录 ADDED/UPDATED/STALE 计数
5. 若合并阶段异常 → 整体回滚，task=FAILED，资源保持旧状态（不会半截）
```

**为什么必须 staging**：直接边拉边写，一旦第 3 页超时，资源树就变成"半个新 + 半个旧"，且无法判断哪些该删。staging 让"拉取"和"生效"分离，生效是一个原子操作。

**快照指纹**：对本次全量结果按 `code` 排序取哈希。指纹未变则跳过合并（省掉 100 万行的无意义 UPDATE），这是定时全量的性能关键。

#### 对齐用什么算：集合 SQL，而不是内存 diff

百万级镜像不能把两边都拉进内存做比对。用 staging 表当"本轮远端基准"，三条集合语句完成对齐：

```sql
-- ① 消失：本地有、本轮暂存无
DELETE FROM res_channel d
 WHERE d.source_platform_id = ?
   AND NOT EXISTS (SELECT 1 FROM sync_staging s
                    WHERE s.task_id = ? AND s.code = d.code);

-- ② 新增：暂存有、本地无
INSERT INTO res_channel (...)
SELECT ... FROM sync_staging s
 WHERE s.task_id = ?
   AND NOT EXISTS (SELECT 1 FROM res_channel d
                    WHERE d.source_platform_id = ? AND d.code = s.code);

-- ③ 差异更新：无差异不写
UPDATE res_channel d SET name = s.name, online_status = s.status
  FROM sync_staging s
 WHERE s.task_id = ? AND d.source_platform_id = ? AND d.code = s.code
   AND (d.name IS DISTINCT FROM s.name
     OR d.online_status IS DISTINCT FROM s.status);
```

| 方言 | 空值安全比较 | 关联更新 |
|---|---|---|
| PostgreSQL / 瀚高 | `a IS DISTINCT FROM b` | `UPDATE ... SET ... FROM ...` |
| MySQL 8 | `(a <=> b) = 0` | `UPDATE ... JOIN ... ON ... SET ...` |

**第 ③ 条最容易写错**：`SET` 的列集与 `WHERE` 的差异列集必须由同一份元数据生成。手工维护两份清单，迟早出现"改了一边漏了另一边"，表现是"数据明明没变却每次都全量 UPDATE"，百万行级别足以拖垮整轮同步。

#### 单一路径：没有灰度引擎，只有三重验证

本平台从零构建，**不存在"旧同步逻辑"可以回退**。所以不设 `sync.engine` 这类三态开关——那会为一条不存在的分支留代码、留测试、留文档，最终变成两套逻辑都要维护。

替代它的是进入 M2 验收前必须完成的**三重验证**：

| 手段 | 做法 | 拦什么 |
|---|---|---|
| 三条 SQL 的方言单测 | 同一份元数据生成 PG / MySQL 两套 SQL，固定数据集断言新增 / 更新 / 删除三种结果，并断言**无差异时影响行数为 0** | SQL 写错 → 漏删、多删、全量重写 |
| 三档规模测试 | 10 万 / 50 万 / 100 万通道各跑一次全量，记录耗时、影响行数、锁等待 | PG 65535 参数上限、长事务、锁超时 |
| 影子对比 | 上线前用同一份目录报文，分别跑"内存比对"与"集合 SQL"，逐字段 diff 结果集，必须完全一致 | 两种实现的语义差异（null 处理、排序、大小写） |

**回滚能力来自结果可验证，不来自配置开关。** 三条都过了，才允许接真实平台。

> 若首轮上线仍需要保底，用**动作级开关**而不是引擎级开关：
>
> ```
> sync.delete.mode = mark   # 只标记待删（写 sync_record + 日志），不真删
> sync.delete.mode = real   # 真实删除（默认）
> ```
>
> 它只影响"删除"这一个动作，链路不变、数据路径不变；观察一轮无异常后改配置即可。这与"换一套引擎"有本质区别——前者可逐步对比、可定位、可单独验证，后者是两套代码各跑各的，差异只能靠事后发现。

#### 组织归属的 4 步回填

上游报文里的 `parent_code` 不保证是组织编码——可能是设备、分组，或者平台域本身。因此设备归属必须按固定顺序回填，**顺序不可调换**：

| 步 | 依据 | 命中后 |
|---|---|---|
| ① 本轮组织直接命中 | `parent_code` = 本轮已落库的组织编码 | 挂该组织 |
| ② 历史绑定恢复 | 本平台保存过的"设备 ↔ 组织"人工绑定（`device_org_binding`） | 挂绑定组织，并继续参与后续同步 |
| ③ 平台根 | `parent_code` = 来源平台的域编码 | 挂该来源的根组织（自动创建，如"XX 平台"） |
| ④ 兜底异常组织 | 以上都不命中 | 挂 `[未分类]`，保留 `status=ACTIVE` 但打标 `org_missing` |

第 ④ 步的影响行数就是本轮"异常设备数"，必须进同步摘要并在界面高亮——**不隐藏异常，是排障的起点**。

#### 组织缺失设备的延迟重试

分批传输下**批序不保证**：设备可能比它所属的组织先到。如果 ④ 判定的异常就永久留在 `[未分类]`，一次全量下来可能几千台错位。

| 项 | 规则 |
|---|---|
| 触发 | 本轮 finish 后异常数 > 0 即登记延迟重试 |
| 防抖 | 延迟 N 秒执行（默认 30s），期间若新一轮开始则合并，不重复跑 |
| 强制触发 | 等待超过上限（默认 10 分钟）强制跑一次，避免永远等不到 |
| 复查范围 | 只重算 `org_missing = 1` 的设备，重新走 ①~④ |
| 终止 | 本轮全量成功收尾后**取消**重试计划；仍无法归属的保持标记，等下一轮 |

> 这条与 3.8.4 的 `[未分类]` 是配套的：前者负责"先接住"，这里负责"接住之后归位"。只做前者，异常组织会变成垃圾场。

### 3.8.3 失败与重试

| 失败类型 | 重试策略 | 上限 |
|---|---|---|
| 连接失败/超时 | 指数退避 30s → 60s → 120s → 300s | 5 次后 task=FAILED，等下次定时 |
| 部分页失败 | 从失败页续拉（记录 offset） | 3 次后整体失败 |
| 合并失败（约束冲突） | 记录冲突项到 `sync_record`，跳过该条继续 | 不重试，转人工 |
| 上游返回空目录 | **不视为删除**，视为异常（打警告，不触发消失计算） | 需二次确认才允许"清空" |

最后一条特别重要：上游故障时常常返回空目录，如果直接按"消失"处理，会把本地所有镜像资源标失效，恢复后又要全量重建。**空目录 = 异常**，必须人工确认。

### 3.8.4 资源删除 vs 下线 vs 失效（回答 C3，需求 3.3 重点）

| 状态 | 含义 | 触发 | 数据是否保留 | 能否播放 | 出站影响 |
|---|---|---|---|---|---|
| `ACTIVE` | 正常 | 同步/创建 | 是 | 能 | 保持共享 |
| `OFFLINE` | 来源明确告知离线 | 上游 Notify 或心跳失败 | 是 | **否** | 推荐 STATUS=OFF（目录项仍在） |
| `STALE` | 本次全量未出现，未确认删除 | 全量差异 | 是（宽限期 24h） | 否 | 暂不撤销，等确认 |
| `REMOVED` | 确认删除 | 上游删除通知 / 宽限期后仍缺失 / 管理员确认 | 软删（`removed_at`） | 否 | **等同于撤销共享**：同事务置 `out_share.ref_alive=0` + 生成 `DELETE` 事件 + 映射置 `TOMBSTONE` |

三条规则：

1. **用户永远不能主动删**（INBOUND 资源），界面无删除入口。
2. **系统删除必须留痕**：`removed_at` + `sync_record` + `audit_log` 三层记录，可回答"什么时候因为什么被删的"。
3. **恢复机制**：`STALE` 的上游资源重新出现时，直接回 `ACTIVE`（不需要人工），因为编码未变。

#### 消失的级联副作用（一个资源消失 = N 个上级各一条 DELETE）

上游删除通知到达时，本平台要做的不是"删本地一行"，而是一次**跨三张表的事务**——这是最容易漏、后果最持久的地方：

| 步 | 动作 | 为什么必须同事务 |
|---|---|---|
| 1 | `res_*` 置 `status=REMOVED` + `removed_at` | 判定消亡的起点，后续都以它为准 |
| 2 | `out_share.ref_alive = 0`（该资源的**所有**平台共享项） | 若分开提交，会出现"资源已删、共享仍活"的窗口，上级此时点播会命中一条死共享 |
| 3 | 每个受影响平台各插一条 `outbox(DELETE)` | 事件与 `ref_alive` 必须同生同灭，否则要么漏推、要么重复推 |
| 4 | `out_code_map.state = TOMBSTONE` | 保留映射，供"资源恢复后复用原码" |

四条实现要求：

1. **不删 `out_share` 行，只置 `ref_alive=0`**。删行会丢掉"这个通道曾共享给谁"，恢复时要人工重配；置 0 可在恢复时自动置回 1。
2. **按平台聚合，不按通道发散**。一个设备消失（含 N 个通道）时，同一平台的 DELETE 要聚成少量事件，不能"通道数 × 平台数"地发。
3. **点播与对账都要校验 `ref_alive`**。DELETE 推送成功前上级可能仍在点播，此时必须直接拒绝，而不是向一条已 REMOVED 的通道取流。
4. **资源恢复是另一条路径**：REMOVED 的资源在上游重新出现时，`ref_alive` 置回 1 并生成 `ADD` 事件；暴露码优先复用该资源自己的墓碑码（按 `(platform_id, native_code)` 命中），**不同资源之间仍不复用序号**。

> 这套设计的意义：**"消失"和"撤销共享"不是两个功能，而是同一个动作的两个触发源**——一个由用户点，一个由上游推。共用一套逻辑，才不会出现两处各写一遍、然后慢慢跑偏。

#### 两个删除闸门（防止一次坏报文清空本级）

3.8.3 已规定"空目录 = 异常"。但还有更隐蔽的一种情况：**上游发来的不是空目录，而是少了 90%**——上游重建了目录，或分页丢了一批。此时差异计算会把缺的部分全部判为"消失"。

两个闸门都必须在**删除执行之前**判断：

| 闸门 | 条件 | 动作 |
|---|---|---|
| **G1 空批保护** | 本轮暂存 0 行，但本地该平台有 N 行 | **整轮回滚**，`task=FAILED`，错误码 `SYNC_EMPTY_STAGING` |
| **G2 批量删除保护** | 预计删除数 > 本地行数 × `delete_guard_ratio`，且本地 > 1000 行 | **只跳过删除**，新增与更新照常执行；摘要明写"删除已跳过"，并给出二次确认入口 |

三条规则：

1. **跳过的是"删除动作"，不是整轮**。新增与更新仍然生效，避免"因为删不掉，所以新数据也进不来"。
2. **跳过必须可见**。同步摘要、任务详情、事件推送三处都要带这个标记，否则运维会以为已经全量对齐。
3. **真实删除要二次确认**。确认时展示"预计删除 N 条，其中 X 个正在共享"，并要求输入平台名确认，避免误点。

阈值默认 `0`（关闭）是刻意的：它依赖各平台的资源规模，没有通用安全值。但**首次接入、以及大版本升级后的第一次全量，必须手工设为 0.2**。

### 3.8.5 多平台并行同步

| 维度 | 方案 |
|---|---|
| 并发度 | 全局并发上限（默认 3 个平台同时全量），单平台串行 |
| 限流 | 每平台令牌桶（默认 5 QPS），避免打爆上游 |
| 隔离 | 单平台失败不影响其它平台；任务表按平台独立 |
| 优先级 | 手动 > 定时 > 通知补拉；通知实时处理不进队列（单条很轻） |
| 幂等 | 同一平台同一时刻只允许一个全量任务（DB 唯一约束 + 分布式锁，不用进程内锁，见 3.13.5） |

### 3.8.6 同步可观测

`sync_task` 记录：平台、类型、开始/结束、进度、ADDED/UPDATED/STALE/FAILED 计数、错误摘要。
`sync_record` 记录：单条资源的变更（`code`、`change_type`、`before/after` 摘要、时间）。

界面只需三处：平台卡片（最近同步时间/结果）、同步中心（任务列表）、详情抽屉（单条变更）。排障时能回答"这条通道是几点变的、变前叫什么"。

以上是**用户可见的进度**。服务端留底（轮次台账、原始报文快照、残留清理、互斥与冷却）见 3.13。

## 3.9 资源共享方案

### 3.9.1 共享的三段结构（回答 A5）

给一个上级平台的共享，永远是三段：

```
① 目标平台（out_share.platform_id）
② 挂载位置（out_share.group_id → out_group：该平台的 215/216 虚拟组织树）
③ 共享项（out_share 行：某个资源 → 挂在某个组下）
```

**为什么必须有 ②**：GB28181 上级看到的目录是 `DeviceID + ParentID` 的扁平列表，它对"组织"的理解就是"父节点是分组编码"。所以本平台必须为每个上级维护一棵"虚拟组织树"，通道挂在这棵树上。**本地组织树不能直接当它用**（见 2.3）。

### 3.9.2 共享范围的两种模式（关键设计）

需求同时要求"精细选择"和"自动跟随变化"，纯快照或纯规则都不满足：

| 模式 | `out_share.scope_mode` | 语义 | 新增资源时 | 适用 |
|---|---|---|---|---|
| **显式** | `EXPLICIT` | 用户逐个勾选的资源 | 不自动共享，需人工加 | 只共享少数重点通道 |
| **子树** | `SUBTREE` | 记一条"组织 X（含子树）"，挂到某虚拟组织 | **自动**：新资源 `org_path` 命中前缀时，自动生成共享项 | 整个组织共享出去（最常用） |

实现要点：

- `SUBTREE` 行存的是"规则行"（`ref_type=ORG`），不是把子树展开成 N 行。
- 资源变更事件到达时：查 `out_share WHERE scope_mode='SUBTREE' AND org_path 前缀命中` → 若尚未存在显式行，则生成一条"派生共享项"（`derived=1`）。
- 用户在子树内单独剔除某个通道 → 生成一条 `EXPLICIT + enabled=0` 的排除行，优先级高于规则。
- 这样"组织共享"是声明式的，"剔除"是覆盖式的，两者不冲突。

```sql
-- out_share 增补字段
scope_mode  VARCHAR(16) NOT NULL DEFAULT 'EXPLICIT'  -- EXPLICIT / SUBTREE
derived     TINYINT     NOT NULL DEFAULT 0           -- 1=由规则派生
enabled     TINYINT     NOT NULL DEFAULT 1           -- 0=排除（用于剔除）
```

### 3.9.3 编码映射（回答 A4 / B7）

**核心规则：入站不改码，出站必重编号。**

| 场景 | 资源原始码 | 出站暴露码 | 原因 |
|---|---|---|---|
| 本地自建资源 | 已在本平台 SIP 域下（前 10 位 = 本平台域） | **透传** | 国标要求 DeviceID 属于本平台域，本地资源天然满足 |
| 入站资源（本地共享） | 属于**来源平台**的域 | **重编号** | 上级只认本平台域内的编码；直接透传会造成"上级看到别人的域"，且与本地码冲突 |
| 入站资源（转发） | 同上 | **重编号** | 同上，且必须与其它来源的码隔离 |
| 重编号后再次共享 | — | 复用已分配的暴露码 | 编码一经分配**不随资源变化**，否则上级会认为"旧通道消失 + 新通道出现" |

暴露码生成规则：

```
暴露码 = 本平台SIP域(10位) + 原类型段(3位) + 序号(7位)
        └── 来自 platform.local_domain      └── 200设备/131通道/215业务分组/216虚拟组织...
序号按平台内单调分配，删除不复用（墓碑保留）
```

**按平台独立映射**（`out_code_map.platform_id`）：不同上级可能要求不同域前缀，且独立映射便于"某平台重置"而不影响其它平台。

**逆向解析链**（上级点播时）：

```
上级 INVITE(exposed_code)
   → out_code_map 查 native_code
   → res_channel 查 source_platform_id + media_hint
   → MediaAdapter 向来源平台 INVITE(原始码)
```

这条链必须是**纯查询**，不能有"如果查不到就猜"的逻辑，否则会点错通道。

#### 出站必须携带全局身份（跨路径识别的前提）

重编号解决了"编码冲突"，但代价是**丢掉了资源的原始身份**——B 看到的是新码，不知道它原来是 A 的哪一台。所以出站时要在目录项里同时带三个扩展字段：

| 扩展字段 | 含义 | 示例 |
|---|---|---|
| `OriginPlatformId` | 最上游平台标识 | `34020000002000000001`（A 的国标码） |
| `OriginCode` | 最上游原始编码 | `34020000001310000001` |
| `OriginChain` | 平台链（可选，用于完整追溯） | `34020000...001,34020100...001` |

三条规则：

1. **恒带**：无论资源来自本地、入站还是转发，出站目录项都带 `OriginPlatformId + OriginCode`（本地资源则是本平台 + 自身码）。
2. **只增不改**：全局身份随资源共享生命周期不变；即使资源改名、换组、换暴露码，`OriginCode` 也不变。
3. **可缺失但要诚实**：若上游未提供原始身份，本平台只能填"直接来源"，并在 `code_chain` 里标记链长为 1 —— 下游据此知道"这不是全链"，而不是误以为追溯完整。

> 这一条是"跨路径识别"能自动化的关键：**A→本 拿到的 `(A, X)` 与 A→B→本 拿到的 `(A, X)` 能直接对上**，不需要靠名称/IP 猜。国标报文没有专门字段承载它，通常放在 `Device` 节点的扩展元素或 `Info` 扩展里；与主要上游对接时需要确认对方是否透传，不透传则退化为人工确认（见 3.10.3）。

### 3.9.4 冲突处理

| 冲突类型 | 检测时机 | 处理 |
|---|---|---|
| 暴露码与本平台已有资源码相同 | 分配映射时 | 换下一个序号（自动） |
| 同一资源被两个共享项映射到同一平台 | 保存共享时 | 唯一键拦截，提示"该资源已共享到该平台" |
| 上级已存在同名/同码节点（上级侧拒绝） | 推送失败 | 记录 `last_error`，标记"需人工确认"，不自动改码（改码会让上级产生孤儿节点） |
| 资源在上级侧挂载的组已被删除 | 推送时 | 自动挂回该平台的根组，并告警 |

### 3.9.5 推送与撤销

- **推送**：资源变更/共享变更 → `outbox(PENDING)` → Dispatcher 按平台分片投递 → `200` 即 `SENT`。
- **撤销**有两个触发源，走同一套逻辑：① 用户主动撤销共享；② 资源被判定 `REMOVED`（上游删除通知，或宽限期后确认消失，见 3.8.4）。两者都**不删行、只置 `out_share.ref_alive=0`**，生成 `DELETE` 事件（**不是直接删库**），推送成功后才允许清理映射（映射保留为 `TOMBSTONE`）。
- **为什么撤销要留墓碑**：上级可能延迟或漏收 DELETE，若本平台立刻复用该暴露码，上级下次收到同码 ADD 会认为是"原来的通道变了"，而不是"新通道"。墓碑保证**序号在不同资源之间永不复用**；同一资源消失后恢复，可复用自己的墓碑码。

### 3.9.6 共享状态模型

| 状态 | 含义 | 界面表现 |
|---|---|---|
| `PENDING` | 已配置，尚未推送成功 | 黄色"待推送" |
| `SYNCED` | 最近一次推送成功 | 绿色"已同步 + 时间" |
| `FAILED` | 推送失败，等待重试 | 红色"失败 N 次"，可看原因 |
| `DEAD` | 超过重试上限 | 深红"需人工处理" |
| `REVOKING` | 撤销中 | 灰色"撤销中" |

平台维度的汇总状态 = 该平台下所有共享项的最差状态（`DEAD > FAILED > PENDING > REVOKING > SYNCED`），用于列表页一眼看出哪个平台有问题。

## 3.10 多级级联方案

### 3.10.1 多级拓扑

```
        ┌── 上级B（海康）
        │
本平台 ─┼── 上级C（大华）
        │
        └── 上级D（其他）

本平台 ◄── 下级A（海康）  ◄── 下级A1（更下层，A 汇聚后推给本平台）
```

**关键认知**：多级级联不是"链式转发"，而是"每一个平台都是独立的汇聚点"。本平台只对直接连接负责，不感知 A1 的存在（除非 A 在扩展字段里带了来源链）。

### 3.10.2 防环（回答 B5，需求 3.3 与 11.3 重点）

四道检查，缺一不可，全部在 **share 保存时**与 **publish 投递前**双重执行：

| # | 检查 | 实现 | 拦截效果 |
|---|---|---|---|
| 1 | **反向共享** | 目标平台 ID == 该资源的 `source_platform_id` | 把从 A 收来的资源推回 A（最常见、最致命的环） |
| 2 | **来源链** | 目标平台 ID ∈ 资源 `origin_chain` | A→B→本平台，本平台又推给 A |
| 3 | **跳数** | `hop_count + 1 > maxHop`（默认 3） | 长链路无限延伸 |
| 4 | **自身域** | 资源码前 10 位 == 本平台 SIP 域，但 `source_platform_id != 0` | 绕一圈回到自己（编码泄露/配置错误） |

命中任一 → **保存时直接拒绝**（给明确文案："该资源来自平台 A，不能再共享回 A"），而不是等到推送失败。

### 3.10.3 重复接入与去重（回答 A6 / B6）

先区分两类"重复"，处理方式完全不同：

| 类型 | 例子 | 处理 |
|---|---|---|
| **同源重复** | 同一平台多次全量同步 / 同一平台配了两条连接 | 按 `(source_type, source_platform_id, code)` upsert，天然幂等；两条连接则在保存平台时就拦下 |
| **跨路径重复** | A→本平台 与 A→B→本平台 | 靠"全局身份"（`origin_platform_id + origin_code`）判定，见下文分级 |

#### 分级判定（从"确定"到"猜"）

| 级别 | 判定条件 | 置信度 | 动作 |
|---|---|---|---|
| **L1 精确命中** | `origin_platform_id` + `origin_code` 完全相同 | 100% | **自动建立关联**，无需人工 |
| **L2 码链交叉** | 两边的 `code_chain` 存在相同 `(platformId, code)` 跳 | 高 | 自动建立关联，标记"经中间跳验证" |
| **L3 单侧有身份** | 一方 `origin_code` 为空，另一方有，且 `code` 相同 | 中 | 提示"疑似同一"，人工确认后关联 |
| **L4a 指纹命中** | 设备指纹（IP + 厂商）相同，且通道数接近、名称相似 | 中高 | **预填关联，一次人工确认**（不自动，见下文纪律） |
| **L4b 特征相似** | 无指纹，仅名称/厂商/型号/通道数相似 | 低 | 仅提示，不预填 |
| **L5 无线索** | 以上都不满足 | — | 不提示 |

**L1/L2 是新增能力**，前提是 3.9.3 的"出站携带全局身份"落地。若对接的上游不透传，就退化为 L3/L4；L4a 是最后一道兜底，见下文。

**现实预期（评审直接引用这一条，不要按"全自动"承诺）**：

> **同一直连来源可 100% 幂等去重**——靠 `(source_type, source_platform_id, code)` 唯一键，同一平台重复同步、同一平台配了两条连接，都不会产生重复行。
>
> **跨级去重取决于上游是否透传身份字段**——GB28181 目录报文没有"来源链"标准字段，`OriginPlatformId` / `OriginCode` 只能放在扩展元素里；海康、大华等厂商的上级/下级平台**默认不透传**，跨级场景会大面积退化为 L3（人工确认）或 L4a（指纹预填 + 一次确认）。
>
> 一句话：**跨路径重复识别是"直连全自动、跨级半自动"**。立项范围与验收口径都按这个来，不要承诺"自动识别所有重复资源"。

**为什么不能把它做成全自动**（这是设计取舍，不是能力缺陷）：

| 若强行自动 | 后果 |
|---|---|
| 凭名称/IP 相似就自动关联 | 同一机房的两台同型号设备会被误并，之后共享、点播、删除全部指错对象 |
| 自动关联后不允许人工撤销 | 误并的代价不可逆，只能重建数据 |
| 自动关联参与共享决策 | 一条链路的故障会被"看起来还有另一条"掩盖，故障定位时间变长 |

所以 L1/L2 只在上游主动给出全局身份时才自动；其余一律停在"预填 + 一次确认"，见 3.10.3 下文的指纹纪律与"关联而非合并"。

#### L4 强证据：设备指纹

L1-L3 都依赖"上游愿意告诉你它是谁"。当上游既重编号、又不透传原始身份时，最后的抓手是**设备自身的物理特征**——同一台设备经两条路径进来，即使编码完全不同，它仍然有相同的 IP、厂商和相近的通道数。

**字段落在 `res_device`（不落通道，因为 IP 与通道数是设备维度）**

```sql
ALTER TABLE res_device
  ADD COLUMN device_ip      VARCHAR(64)  NULL COMMENT '设备 IP：优先 SIP 源地址，其次目录 Address 字段',
  ADD COLUMN vendor         VARCHAR(64)  NULL COMMENT '厂商',
  ADD COLUMN model          VARCHAR(64)  NULL COMMENT '型号',
  ADD COLUMN channel_count  INT          NOT NULL DEFAULT 0 COMMENT '该设备下通道数（随同步更新）',
  ADD COLUMN fingerprint    VARCHAR(80)  NULL COMMENT 'sha256(归一化IP|厂商)，IP 缺失时为 NULL',
  ADD KEY idx_fp (fingerprint);
```

**指纹构成与稳定性（最容易做错的地方）**

| 分量 | 是否进哈希 | 原因 |
|---|---|---|
| 归一化 IP（去空白、IPv6 统一小写与压缩） | ✅ 进 | 最稳定的物理特征 |
| 厂商（小写、去空格） | ✅ 进 | 区分"同 IP 不同厂商"的极小概率场景 |
| 通道数 | ❌ 不进，只做**近似度比较** | 通道数会变（新增一路就变）；进哈希会让指纹每次同步都失效 |
| 名称、型号 | ❌ 不进，只做辅助打分 | 可改、可空 |

> 原则：**哈希只放稳定分量，易变分量用于二次校验**。把易变字段放进指纹，等于指纹没用。

**IP 从哪来（不写清楚，字段永远为空）**

| 来源 | 优先级 | 说明 |
|---|---|---|
| SIP 注册/心跳的源地址（实际 socket 对端 / Contact / Via） | 1 | 最可信；但要识别 NAT，内网地址标识能力有限 |
| 目录报文 `Address` 字段 | 2 | 部分平台填写；可能为空或填的是行政区划而非 IP（需格式校验） |
| 设备信息查询响应（DeviceInfo） | 3 | 需额外查询，成本高，按需触发 |
| 都拿不到 | — | `fingerprint = NULL`，降级为 L4b |

**判定细则**

| 条件 | 强度 | 动作 |
|---|---|---|
| 指纹相同 + 通道数差 ≤ `max(2, 10%)` + 名称相似 | 中高 | 预填关联，一次确认 |
| 指纹相同，但通道数差异大或名称不同 | 中 | 提示"疑似同一设备"，列出差异项供核对 |
| 指纹为 NULL | 低 | 退回 L4b 相似度提示 |
| 指纹相同但两边已有不同 `canonical_id` | — | **不合并两个组**，只提示"可能存在第三来源"，由人工决定是否并组 |

**三条使用纪律**

1. **指纹只做"预填"，不做"自动关联"**：IP 会被 DHCP 重分配、会被 NAT 复用、会被人改配置。指纹命中是强证据，不是判决。
2. **指纹变化不自动解除已有 `canonical_id`**：设备换 IP 很常见，若 IP 一变就断关联，历史关联会被全部打散。变化只写入 `sync_record` 并在详情页提示"指纹已变化"。
3. **指纹不参与播放与共享**：它只回答"是不是同一台设备"，不是取流依据，也不是共享凭证。

#### 关联而非合并（关键取舍）

**不做物理合并**（不删行、不搬共享关系），而是建立"同一实体组"：

```sql
canonical_id  BIGINT NOT NULL DEFAULT 0  -- 0 = 自身为组主；非 0 = 指向组主 id
```

| 行为 | 关联后的规则 |
|---|---|
| 列表展示 | 按 `canonical_id` 聚合为一行，显示 `来源 2（海康A / 大华B）`，可展开看每条 |
| 目录树 | 各自留在自己的来源树下（树是视图，不因关联而合并） |
| 播放 | 组内按 `online_status` → 延迟 → 优先级 自动选路；用户也可手动指定"用哪条来源" |
| 共享 | 各自独立共享（`ref_source_platform_id` 不同），也可选"跟随组"（组内任一可用即视为可用） |
| 删除 | 某条 `REMOVED` 只影响该条；组内仍有 `ACTIVE` 时，聚合行依然可播 |
| 同步 | 各自按自己的来源同步，互不覆盖 |

**为什么坚持不物理合并**（这是原结论中唯一保留的部分）：

1. **账号与授权不同**：同一台设备经两条路径进来，对应的上游账号、鉴权、限流配额是两套；合并后无法按来源重试。
2. **可用性不同**：A 路径可能断了，B 路径还通。合并成一条就没有"备选源"了。
3. **共享关系不同**：两条记录可能已分别共享给不同的上级，物理合并会产生"共享项找不到宿主"的悬空数据。
4. **删除语义不同**：A 删了不等于 B 删了，合并后无法表达"部分失效"。

> 一句话：**关联解决"看起来是两台"，不合并保留"实际有两条链路"**。前者是 UX 问题，后者是数据完整性问题，不能用一个动作同时解决。

#### 实现要点

- 建立关联时，组主选取规则：`source_platform_id=0`（本地）优先 > 创建时间最早 > id 最小。
- 关联是**单向**的（子指向组主），避免环形引用；解除关联即把 `canonical_id` 置 0。
- 关联/解除都要写 `audit_log`，且**不允许系统自动解除**（只能人工）。
- 关联后资源总量统计去重：`COUNT(DISTINCT COALESCE(NULLIF(canonical_id,0), id))`。

### 3.10.4 跨级来源追溯（回答 A9）

追溯能力分三档，见 3.6.3；跨级场景的关键差异是**信息由每一跳决定**：

| 场景 | 能拿到什么 | 依赖 |
|---|---|---|
| 本平台直连 A | `(A, X)` 确定，可作全局身份 | 本平台数据 |
| 本平台经 B 拿 A 的资源，B 携带全局身份 | `origin=(A, X)`，与直连完全等价，可直接 L1 匹配 | B 是否透传 `OriginPlatformId + OriginCode` |
| 本平台经 B 拿 A 的资源，B 未携带 | 只能记 `origin=(B, Y)`，链长 1 | 退化为 L3/L4 人工判定 |

**因此"能否跨级追溯/去重"不是本平台单方面能决定的，取决于链路每一跳是否携带全局身份。** 本平台能做的是：

1. 自己出站时**强制携带**（3.9.3），保证下游能追溯；
2. 入站时**尽力解析**（兼容扩展元素、`Info` 扩展、部分厂商的自定义字段）；
3. 把结果如实分级展示（A/B/C 三档），不伪造完整性；
4. 与主要上游在对接阶段确认：是否透传原始身份，作为集成测试的验收项之一。

**界面必须诚实**：详情页显示 `来源：大华B（最上游未知）`，而不是假装知道更上游。若上游带了链，则显示 `来源：大华B → 海康A`。

### 3.10.5 跨级 ID 映射（回答 B7）

每一跳都会重编号一次，形成"码链"：

```
原始通道码 34020000001310000001（A 的域）
   → B 的暴露码 34020100001310000087（B 的域）
   → 本平台暴露码 34029900001310000042（本平台域）
   → 上级 C 看到 34029900001310000042
```

**每一跳的映射表各自独立**（`out_code_map` 按平台隔离），任何一跳重置不影响其它跳。这也是"必须重编号"的另一个理由：如果全链路透传同一编码，上游一改码，整条链断。

## 3.11 视频业务方案（保证 C9）

### 3.11.1 统一播放抽象

无论资源来自哪里，播放都走同一条路径：

```
用户选通道(id)
   → 查 res_channel：source_platform_id、code、media_hint、capability、online_status
   → MediaRouteResolver 解析出"去哪取流、用什么协议、用什么码"
   → MediaAdapter.invite(route) → 得到流地址（本平台 ZLM）
   → 返回播放地址给前端（HLS/HTTP-FLV/WebRTC）
```

**资源模型只提供"线索"，不提供"方法"**：`res_channel` 里没有"如何 INVITE"的逻辑，只有 `media_hint`（如上游通道码、RTSP 模板、设备 IP）。这保证新增协议时资源中心零改动。

### 3.11.2 三种来源的取流路径

| 来源 | 取流方式 | 说明 |
|---|---|---|
| 本地（NATIVE，GB28181 接入的设备） | 平台直接 INVITE 设备 | 设备主动注册到本平台，本平台是 SIP 服务端 |
| 本地（NATIVE，ONVIF/RTSP 设备） | 直接拉 RTSP 或厂商 SDK | 无信令，直接取流 |
| 入站（INBOUND） | 本平台作为"上级"向来源平台 INVITE | 本平台发起，来源平台转发设备流 |
| 转发（INBOUND 被上级点播） | 两级串联：上级 → 本平台 → 来源平台 | 见 3.11.5 |

### 3.11.3 流复用与并发

| 场景 | 处理 |
|---|---|
| 多用户看同一通道同一码流 | 复用同一路 ZLM 流，`viewer_count` 计数，最后一人离开才断开上游 |
| 同时请求同一通道（并发点播） | 分布式锁 + 同一 `streamId` 只允许一个 `INVITING` 会话，第二个请求等待第一个的 SDP，不重复 INVITE |
| 主/子码流 | 不同的 `stream_profile` 视为不同流，各自复用 |
| 空闲回收 | 无观看者超过 N 秒 → 断开，避免长期占用上游带宽 |

### 3.11.4 录像回放

| 来源 | 录像来源 | 实现 |
|---|---|---|
| 本地设备 | 设备 SD 卡 / 本平台云存储 | 设备侧：INVITE 回放 + RTSP 拉取；云存储：直接播文件 |
| 入站资源 | 来源平台的录像 | 本平台向上游发起回放请求（GB28181 的 PLAY），转封装后给前端 |
| 转发的入站资源 | 同上，多一跳 | 上级请求 → 本平台 → 来源平台 |

**首版策略（对应 Q6）**：入站资源**不落本地存储**，只做转发。需要本地留存时，另配"录制任务"（M4 之后）。

### 3.11.5 转发时的两级串联（为什么不能裸转发）

```
上级 INVITE(暴露码)
    │
    ▼
本平台：回 200 + SDP（本平台 ZLM 收流地址）
    │
    ├──► 向来源平台 INVITE(原始码)  ── 来源平台推流到本平台 ZLM
    │
    └──► ZLM 转推/转封装给上级
```

| 方案 | 可行性 | 结论 |
|---|---|---|
| **裸转发**（把上级 SDP 直接转给上游） | 上游只能看到本平台 IP；跨网/跨 NAT 不通；无法录像；无法审计 | ❌ |
| **两级串联**（本平台收流再转发） | 需要额外带宽（进出各一份）；但可控、可录、可审计、可转码 | ✅ |

**代价必须说清**：转发一条 4Mbps 的通道，本平台要占用 8Mbps（入 + 出）。这是级联转发的固有成本，规划带宽时要按"转发通道数 × 码率 × 2"估算。

#### 两级串联的三条硬约束（缺一条就是"卡黑屏 + 僵尸会话"）

拓扑图只是"能跑通"，线上真正会出事故的是下面三条：

| # | 约束 | 规则 | 不做的后果 |
|---|---|---|---|
| 1 | **SDP 必须由本平台构造** | 回给上级的 SDP，`c=`/`o=` 用**本平台 ZLM 对外地址**（`cascade.sdpPublicIp` → `MediaServer.streamIp` → `hostIp`），`m=` 用本平台发送端口且**必须 > 0**；把来源平台返回的 SDP 原样交出去是明确禁止项 | 上级拿到来源侧的内网地址 → 黑屏，且双方都看不到任何错误提示 |
| 2 | **SSRC 分两侧各存一份** | 上级侧 `CascadeSendSession.ssrc` = 上级 INVITE 的 `y=`，`startSendRtp` 与回复 SDP 都用它；来源侧 `GbInviteSession.ssrc` = 本平台分配，设备 200 OK 自报不一致时自适应改写 ZLM 过滤值。两者**不是同一张表的两列** | 两侧混用 → 上级收流端丢包、表现为"有流无画面"；不区分 → 一通道多上级时串流，断流后查不出断在哪一级 |
| 3 | **按源流判活，不靠信令** | 唯一判据是"来源侧还在不在收 RTP"；超时后按 `srcStream` 反查所有上级会话，逐个停推 + BYE | 对端崩溃、拔网线、NAT 超时都不会发 BYE；会话与死流累积，端口与带宽持续泄漏 |

**第 1 条的两个实现细节，都出过事**：

| 细节 | 规则 | 为什么 |
|---|---|---|
| `m=` 端口不能为 0 | UDP 与 TCP-passive 也要填真实端口：回 200 前从发送端口段**预分配** `localSendPort` 并写进 SDP，ACK 后按同一端口 `startSendRtp`；TCP-active 直接用监听端口 | RFC 4566 中端口 0 表示"该媒体流被禁用"，与 `a=sendonly` 直接矛盾。多数上级不读这个字段，但做 SDP 合法性校验的平台会直接判无效 |
| 对外地址要校验，不能直接信节点 IP | 解析顺序 `cascade.sdpPublicIp` → `MediaServer.streamIp` → `hostIp`；拿到空 / `0.0.0.0` / `127.0.0.1` / `::1` 时**回 500 拒绝本次点播**（同时回收已拉起的取流），不回 200 后让上级黑屏；私网地址打 WARN 提示补 `sdpPublicIp` | 显式配置错了必须立刻暴露。静默回退到节点 IP 会把"配错"伪装成"网络不通"，是最难查的一类故障 |

**端口冲突的处理口径**（动作级，不改协议）：预分配端口被 ZLM 报占用时换下一个端口重试（最多 3 次）并打 WARN。此时实际源端口与 SDP 里的 `m=` 不一致——但 UDP 下上级是按**自己** INVITE 声明的 `c=`/`m=` 收流，不校验本平台源端口，TCP 被动同理，所以**可用性优先**。非端口类错误（流不存在、对端不可达）不重试，直接清理并 BYE。

**先纠正一个容易画错的结构**：本平台没有一张"转发会话表"，而是**两个会话对象**，靠源流名关联：

```
GbInviteSession（来源侧：本平台 → 设备/下级平台）
   streamId ──────────────────────┐  源流名（deviceId_channelId）
   ssrc（本平台分配，设备可改写）  │
   rtpPort（ZLM openRtpServer）    │
   serverId（承载源流的 ZLM 节点）  │
                                   │  CascadeSendSession.srcStream = streamId
CascadeSendSession（上级侧：上级 → 本平台）◄─┘
   sendStreamId（主键）
   ssrc（= 上级 SDP 的 y=）
   dstIp / dstPort（上级收流地址，来自上级 SDP）
   localSendPort（本平台发流端口，回填本平台 SDP）
```

一个 `srcStream` 可以对应 **N 条** `CascadeSendSession`——一路源流被多个上级同时点播是正常场景，不是串流。Redis 索引 `cascade:send:by_src:{srcStream}` 存的是 Set，现有实现已经支持。

**字段定稿**（对齐现有实体，Redis JSON 风格用驼峰，不用下划线）：

| 字段 | 所在对象 | 类型 | 含义 | 现状 |
|---|---|---|---|---|
| `streamId` | `GbInviteSession` | String | 源流名（`deviceId_channelId`，回放带时间段后缀） | ✅ 已有 |
| `ssrc` | `GbInviteSession` | String | **来源侧 SSRC**，10 位；设备自报不一致时自适应 | ✅ 已有 |
| `rtpPort` | `GbInviteSession` | Integer | ZLM `openRtpServer` 的收流端口 | ✅ 已有 |
| `serverId` | `GbInviteSession` | String | 承载源流的 ZLM 节点 | ✅ 已有 |
| `sendStreamId` | `CascadeSendSession` | String | 上级侧会话主键 | ✅ 已有 |
| `platformDbId` / `platformServerGbId` | `CascadeSendSession` | Long / String | 哪个上级（回 200 与 BYE 都要用） | ✅ 已有 |
| `ssrc` | `CascadeSendSession` | String | **上级侧 SSRC**，取上级 INVITE 的 `y=` | ✅ 已有 |
| `dstIp` / `dstPort` | `CascadeSendSession` | String / Integer | 上级收流地址（上级 SDP 的 `c=` / `m=`） | ✅ 已有 |
| `localSendPort` | `CascadeSendSession` | Integer | 本平台发流端口，回填本平台 SDP 的 `m=` | ✅ 已有 |
| `transport` | 两者都有 | String | `UDP` / `TCP-passive` / `TCP-active` | ✅ 已有 |
| `srcStream` | `CascadeSendSession` | String | 关联 `GbInviteSession.streamId` | ✅ 已有 |
| `callId` / `fromTag` / `toTag` | 两者都有 | String | Dialog 三要素；**无 `toTag` 不得发 BYE** | ✅ 已有 |
| **`lastRtpTime`** | `GbInviteSession` | LocalDateTime | 最后一次确认收到 RTP 的时刻，**僵尸判定唯一依据**；由巡检采样回写（见下） | ✅ 已有 |
| **`lastSendTime`** | `CascadeSendSession` | LocalDateTime | 最后一次成功 `startSendRtp` 或推流心跳的时刻，仅排障 | ❌ 待加 |
| **`sdpRewritten`** | `CascadeSendSession` | Boolean | 回复上级 SDP 时置 `true`，用于回归断言（防某次改动把来源 SDP 直传出去） | ✅ 已有 |

**为什么超时阈值不做成会话字段**：超时是**上级平台的网络特性**（专网 30s、公网 60s），不是某一次会话的特性。放配置更合理——会话对象只存时间戳，判断时用"时间戳 + 生效阈值"。**首版落地口径**：只有全局 `gb28181.cascade.rtp-timeout-sec = 30`（设 0 或负数关闭巡检）；`platform.rtp_timeout_sec` 按上级覆盖**暂缓**——`gb_parent_platform` 目前没有该列。

**`lastRtpTime` 从哪来（不写清楚就永远是 null）**：

先说结论：**ZLM 不提供"最后一次收流时刻"**。实测 2024-08 构建 + master 源码，`getMediaList` 每项只有 `createStamp`（流创建 unix 秒）、`aliveSecond`（取 `MediaSource::getAliveSecond()` = `_ticker.createdTime()/1000`，**也是创建时刻**）、`bytesSpeed`、`readerCount` / `totalReaderCount`，**没有 `origin_stamp`**。所以只能由本平台巡检采样后自己回写。

| 来源 | 优先级 | 说明 |
|---|---|---|
| 巡检采样 `bytesSpeed > 0` | 1 | 定时任务（10s 一轮，`GbHealthScheduledTasks.sweepCascadeZombieSources`）拉 `getMediaList`，有码流就把 `lastRtpTime` 刷成当前时刻。最小写间隔 5s，避免每轮把整个会话 JSON 重写一遍 |
| ZLM `on_rtp_server_timeout` 回调 | 2 | ZLM 自身 `rtp_server_timeout`（默认 15s）触发即视为源流已死，直接进入清理，不等巡检 |
| ~~`origin_stamp`~~ | — | **该字段不存在**（早期设计稿笔误），已废弃 |

只看 `bytesSpeed` 判活会误杀（HLS 拉流、暂停、切片刷新都有瞬时 0 码流），所以判定分五档（`GbInviteLiveness.probe`）：

| 采样结果 | 结论 | 动作 |
|---|---|---|
| 流不在节点上 | `GONE` | 进阈值判定（对端崩溃后 ZLM 的 RTP 端口超时会自己注销流） |
| 流在、`bytesSpeed > 0` | `FLOWING` | 刷新 `lastRtpTime` |
| 流在、`bytesSpeed = 0`、有人观看 | `WATCHED` | **不判死** |
| 流在、`bytesSpeed = 0`、没人看 | `SILENT` | 疑似僵尸，进阈值判定 |
| 节点不可达 | `UNREACHABLE` | 本轮不判——一次网络抖动不能把所有会话当僵尸清掉 |

两个易错点：① 同一路流 ZLM 会按 schema（rtsp / rtmp / hls / ts / fmp4…）各返回一条，`bytesSpeed` 与 readers 都要**取最大值**，不能命中第一条就下结论；② 只有 `READY` 状态的 `PLAY` / `PLAYBACK` 参与判死——`INVITING` 还没起流，`DOWNLOAD` / `RECORD` 是 TCP 文件流，本就没有连续 RTP。

**僵尸清理流程（复用现有索引，不新增全表扫描）**：

1. 定时任务（默认 10s）检查 `lastRtpTime` 是否超过全局阈值（`lastRtpTime` 为空时退回 `readyTime` 起算，否则刚就绪的会话永远判不出来）。
2. 按 `cascade:send:by_src:{streamId}` 取出 `Set<sendStreamId>`，逐个加载 `CascadeSendSession`；没有上级在推则直接回收来源侧。
3. 对每个上级会话：先 `stopSendRtp`，再**有 `toTag` 才发 BYE**（没有 `toTag` 的对端会直接丢弃）→ 删会话与索引。
4. 最后按现有 `timeoutSession` 清理来源侧的 ZLM RTP server 与 SSRC 占用。

> 第 3 步顺序不能反：**先停推流，再发 BYE**。反了会出现"BYE 已发、推流还在"的窗口——上级记成已挂断，媒体面仍在收包。

**三个新字段的落地成本**：它们都在 Redis JSON 里，**加字段不需要 DDL，旧数据反序列化为 null 即可**。相比之下若做成数据库表，加列要走变更脚本与灰度。这也是会话对象继续放 Redis 的理由之一。

优先级：第 1、2 条是**出厂必须正确**（错了每次点播都失败，现象是"黑屏无报错"）；第 3 条是**运行时兜底**（错了表现为偶发残留，往往几天后才发现）。三条在 M5 开工前把字段加进实体即可，不必等表结构评审。

### 3.11.6 播放状态与失败语义

| 状态 | 含义 | 界面提示 |
|---|---|---|
| `INVITING` | 正在向上游/设备发起 | "连接中…"（超时 15s） |
| `PLAYING` | 流已就绪 | 播放器 |
| `FAILED_OFFLINE` | 上游通道离线 | "该通道当前离线（来源：海康A）" |
| `FAILED_UPSTREAM` | 上游拒绝/超时 | "来源平台无响应，请稍后重试" |
| `FAILED_UNSUPPORTED` | 编码不支持 | "该通道编码格式不支持，需转码" |

失败原因必须**带来源**，用户才能判断该找谁（本地设备 vs 外部平台）。这是"统一管理不影响视频能力"的落地细节（C9）。

### 3.11.7 资源变更事件的推送与超量降级

同步或共享动作完成后，要通知两类消费者：**本平台前端**（刷新列表与树）和**对外订阅方**（3.12.1 的 SSE 集成方）。两者共用同一套事件与同一条降级规则。

**事件形态只有两种**：

| 形态 | 内容 | 适用 |
|---|---|---|
| `CHANGED_DETAIL` | 逐条明细：`code`、`change_type`（ADDED / UPDATED / REMOVED）、关键字段 | 变化量小 |
| `REFRESH_ALL` | 无明细，只说"某来源 / 某平台的数据已刷新" | 变化量大，或结构变化 |

**降级规则**（阈值 `event_detail_max`，默认 500）：

| 情况 | 推送 | 理由 |
|---|---|---|
| 组织树有重建（新增 / 移动 / 删除组织） | `REFRESH_ALL` | 增量补不动树形结构 |
| 变化总数 ≤ 阈值 | `CHANGED_DETAIL` | 实时体验最好 |
| 变化总数 > 阈值 | `REFRESH_ALL` | 20 万条明细会把连接和前端一起打爆 |
| 删除被闸门跳过（3.8.4） | `REFRESH_ALL` | 明细语义已不完整，不能只发一半 |
| 有影响行数但明细回读为空 | `REFRESH_ALL` | 并发删改导致，安全优先 |
| 无任何变化 | **不推送** | 避免"心跳式刷新" |

**两个实现细节，顺序不能反**：

1. **变化范围要在写库前确定**。删除 / 插入 / 更新一旦执行，差异就消失了。必须先按 `task_id` 从 staging 读出"哪些 `code` 会变"，再执行写库。
2. **明细内容要在写库后、同一事务内回读**。只有写完之后，暴露码、组织 id、能力集才是最终值；事务内回读能看到未提交数据，且与最终提交结果严格一致。

**SSE 侧的额外要求**：`REFRESH_ALL` 也必须携带单调递增游标（`Last-Event-ID`）。否则订阅方断线重连后无法判断"我错过的是一批明细，还是一次全量刷新"。规则一句话：**事件可以合并，游标不能跳号**。

## 3.12 权限与安全方案

### 3.12.1 信任边界与三类主体

先划边界，再谈"谁能做什么"——否则安全设计会退化成"每个接口都加个 token"。

| 边界 | 外面是谁 | 进来必须过的关 | 不过的后果 |
|---|---|---|---|
| 入站信令（SIP 5060/5061） | 任何知道本平台 SIP 地址的主机 | 注册：摘要认证 + `platform` 表存在且启用；报文：来源必须是已注册端点 | 空壳平台可被任意主机注册，目录被灌入脏数据 |
| 入站点播（INVITE） | 已注册的上级平台 | 暴露码 → `out_code_map` 反查 → `out_share` 命中，查不到直接拒绝 | 猜到编码就能播未共享的通道 |
| 管理 API（浏览器） | 办公网 / 公网 | Token + RBAC + 数据范围；强制 HTTPS | 凭证、目录、SDP 明文过网 |
| 对外订阅（SSE / API） | 集成方 | API Key + 签名 + `scope` 绑定 + 推送前二次过滤 | 越权看到其他下级平台的资源 |
| 出站推送（本平台 → 上级） | 上级平台 | 平台凭证加密存储；失败可告警可重试 | 凭证库泄露等于所有上级同时被接管 |
| 媒体面（RTP / SDP） | 任何能发包的主机 | 只接收来自本会话对端地址的 RTP；端口按会话分配 | 任意主机往端口推流，造成串流或占满带宽 |

**一条总原则：每个入口单独校验，不继承上一道关卡的结论。**

- SIP 注册通过了，不代表后续 INVITE 合法（注册只证明"这台机器在这个地址上"，不证明"它有权播这个码"）。
- Token 有效，不代表能看这个组织（Token 只证明"是谁"，数据范围要另外判）。
- 这种"逐入口校验"看起来重复，但它让每个入口的失效域是隔离的——一个校验写错，不会连带其它入口。

三类主体：

| 主体 | 认证方式 | 授权方式 | 典型操作 |
|---|---|---|---|
| 平台用户（人） | 账号密码 / SSO | RBAC + 数据范围（组织路径） | 资源维护、共享配置、播放 |
| 外部视频平台 | SIP 摘要认证（国标）/ 厂商凭据 | 接入白/黑名单 + 方向能力位 | 注册、拉目录、点播 |
| 集成方（SSE/API） | API Key + 签名 | `event_subscription.scope`（平台/组织路径） | 订阅变更、查目录 |

### 3.12.2 资源级权限

```
角色（能做什么操作） × 数据范围（能看哪些组织）
    角色：viewer / operator / resource_admin / platform_admin
    范围：user_org_scope（组织路径前缀集合，可为空=全部）
```

判定顺序：**先范围，后角色**。用户在范围内的资源才能执行角色允许的操作。INBOUND 资源的"写"操作在角色层就不存在（天然拒绝），不需要靠范围兜底。

### 3.12.3 共享范围即授权

上级平台能看到什么，**完全由 `out_share` 决定**，不需要额外的"平台权限表"。这是本设计的一个简化：

- 共享项存在 → 该平台可见（推送目录、接受点播）
- 共享项不存在 → 即使上级拿编码来点播，也返回 404/拒绝

这样"配置共享"和"授权"是同一个动作，用户不需要在两处维护（对应需求 11.4 的诉求）。

### 3.12.4 凭证保护

| 要求 | 做法 |
|---|---|
| 不明文存储 | `platform_credential` 字段 AES-256 加密，密钥来自环境变量/KMS，不入库 |
| 不出现在响应 | 查询接口只返回掩码（`****`）与"已配置"标记 |
| 不进日志 | 日志脱敏；异常堆栈里禁止带 SDP/SIP 报文原文 |
| 可轮换 | 支持"更新凭证"不中断已有会话；旧凭证保留 1 个周期便于回滚 |

**轮换周期（建议值，可配）**：

| 对象 | 周期 | 为什么是这个周期 |
|---|---|---|
| SIP 摘要密码 | 180 天 | 国标对接改密码必须双方同时改，太频繁会让合作方干脆不换 |
| API Key | 90 天 | 支持双 Key 并存：先在集成方切换，确认无流量后再禁用旧 Key |
| 加密主密钥（AES-256） | 1 年，或泄露时立即 | 主密钥轮换要重加密整列，成本高；用"主密钥 + 数据密钥"两层，可把重加密降为改指针 |

**GB35114 决议（附录 B #13）**：**首版不启用**，但 `platform_credential` 建表即带 5 个占位字段（`cert_id` / `sm2_priv_ref` / `sm4_key_ref` / `cipher_suite` / `expire_at`，全可空，`cipher_suite` 默认 `NONE`）。原因：真到要用时，凭证从"账号密码"要升级为"设备证书 + 私钥引用"，如果表结构没预留，就是改表 + 改 SIP 栈 + 重估媒体链路的连锁返工；而占位成本几乎为零。此外**证书到期是硬失败**（不像密码错了还能重试），一旦启用，`expire_at` 必须提前 30 天告警，否则表现为"某天早上所有级联突然断开"。

### 3.12.5 防越权与防滥用

| 风险 | 措施 |
|---|---|
| 未授权订阅其他平台资源 | 订阅时校验 `scope` 与订阅方身份绑定；事件推送前二次过滤 |
| 上级点播未共享的通道 | 按 `out_code_map` 反查，查不到即拒绝（不做"猜码"） |
| 循环共享 | 3.10.2 四道检查 |
| 同步打爆上游 | 每平台令牌桶 + 全量并发上限 |
| 大量导出资源 | 导出接口限流 + 审计 |

### 3.12.6 审计

必审：平台凭证变更、共享新增/撤销、资源删除（系统删除也算）、批量导出、播放（可选，量大时按采样）。
审计记录包含：操作人、时间、对象、变更前后摘要、来源 IP。**审计表只追加，不提供修改接口**。

### 3.12.7 传输加密与暴露面

3.12.1 划的是"谁能进来"，这一节回答"进来之后走的路是不是敞开的"。

| 通道 | 建议 | 理由 |
|---|---|---|
| 管理 API / 前端 | **强制 HTTPS**（HSTS），80 端口只做 301 | 凭证、目录、SDP 全在这条链路上 |
| SIP 信令 | 默认 UDP 5060（国标兼容必需）；对要求安全的对端开 TLS 5061 | 多数老平台不支持 TLS，强制会直接接不通——所以是"按对端能力协商"，不是全局一刀切 |
| 对外 SSE / API | 强制 HTTPS + IP 白名单（见附录 B） | 事件流含全量目录索引，泄露等于拿到整张资源表 |
| RTP 媒体 | 端口段固定 + 来源 IP 校验；**不加密** | SRTP 与国标设备互通性差；真正的加密需求走 GB35114 整体方案，不是单点加 SRTP |
| 应用 ↔ DB / Redis | 同机或受限专网，不额外加密 | 单机单库部署，加密没有实际收益，反而多一层故障点 |

**暴露面清单（部署时逐项确认是否只对内网开放）**：

| 端口 | 用途 | 开放范围 |
|---|---|---|
| 5060/udp | SIP 信令 | 对已登记的下级/上级平台开，不对公网开 |
| 5061/tcp | SIP over TLS | 仅在启用 TLS 时开 |
| 443/tcp | 管理 API + 前端 | 只对内网办公网开 |
| RTP 端口段（默认 30000–30500） | 媒体收流 | 仅对已登记平台地址开 |
| ZLM 播放端口（HTTP-FLV / WebSocket） | 前端取流 | 仅对管理网开 |

**一条运维红线**：ZLM 的 HTTP-FLV / WebSocket 端口一旦对公网开放，等于**绕过 3.12.3 的全部共享授权**——任何人知道流 ID 就能看。所以前端不能直连 ZLM 裸流地址，必须经本平台接口换取**短期播放凭证**再取流（凭证与 `out_share` 命中绑定，默认有效期 10 分钟）。

## 3.13 同步运行保障

> 本章不新增业务能力，只回答一个问题：**同步跑完之后，怎么证明它跑对了、出了问题怎么查、跑挂了谁来收尾。**

### 3.13.1 轮次台账（每轮一行）

`sync_round` 是运维的第一现场，不是"日志的替代品"。它与 `sync_round_snapshot`（3.13.2）都属于**运维辅助表**，不计入 3.5.3 的 15 张业务表。

| 字段 | 说明 |
|---|---|
| `task_sn` / `platform_id` / `platform_name` | 哪一轮、哪个平台 |
| `begin_time` / `end_time` / `status` | `RUNNING` / `DONE` / `FAILED` |
| `org_recv` / `dev_recv` | 收到的条数（去重后 / 原始） |
| `org_insert` / `dev_insert` / `dev_update` / `dev_delete` / `dev_dup` | 落库结果，全部取自真实影响行数 |
| `delete_skipped` / `guard_ratio` | 是否被闸门跳过、当时的阈值 |
| `error_code` / `error_msg` | 失败原因，截断存储 |
| `summary` | 可直接展示的一句话摘要 |

**必须落盘的两个字段**：`delete_skipped` 与当时的 `guard_ratio`。否则两周后没人能回答"那天为什么没删"。

与 `sync_task` 的分工：`sync_task` 是**任务状态**（用户看的进度，可重跑），`sync_round` 是**执行事实**（运维看的对账依据，不可重写）。两者不能合并。

### 3.13.2 原始报文快照（可选）

| 项 | 建议 |
|---|---|
| 存什么 | 本轮收到的原始目录行（组织 / 设备 / 通道），只保留比对所需字段 |
| 为什么 | 唯一能回答"**是上游没发，还是我们弄丢了**"的证据 |
| 保留 | 最近 2 轮（含当前轮），超出即清 |
| 清理 | 有分区能力的库每轮一个分区，用 `DROP` 秒级清理；无分区按轮次分批 `DELETE`（每批 5 万行，避免长事务） |
| 开关 | 默认关闭，排障时打开；保留轮数可配 |

**容量提示**：100 万通道 × 2 轮 × 每行约 200 字节 ≈ 400MB，可接受。但必须在设计时就定死"只存最近 N 轮"，否则这张表会长成库里最大的表。**它是单库体积唯一会翻倍的来源**，容量总预算见 5.2.1；交付档位见 6.3 的 C 档（做表与开关，默认关闭）。

### 3.13.3 三条旁路纪律

审计与快照是**纯旁路**，永远不能反过来影响主流程：

1. **异步**：写入走独立单线程池，同步线程只做一次浅拷贝 + 入队，不碰数据库。
2. **可丢**：队列满时丢弃快照并记一条 warn，**绝不阻塞同步**。但收尾任务必须预留队列位置，否则轮次会永远停在 `RUNNING`。
3. **可关**：`sync.audit.enabled=false` 时所有入口空转，不产生任何数据库交互。

反过来，**staging 不是旁路**：它是合并正确性的前提，写失败必须让本轮失败（返回失败而不是静默丢数据）。两者的区别要在代码里显式体现，不能都写成"try/catch 吞掉"。

### 3.13.4 残留清理（三道）

| 时机 | 清什么 | 为什么需要 |
|---|---|---|
| 正常收尾 | 成功：清本轮 + 同域历史残留；失败：**只清历史，保留本轮** | 失败轮的数据是最有价值的现场 |
| 启动后延迟一次 | 上次运行遗留（被 kill / 断电） | 内存状态可自愈，磁盘不能 |
| 运行期周期 | `recv_time` 早于保留时长（默认 24h）的残留 | 收尾线程自身也可能异常退出 |

清理必须是**独立线程 + 异常吞掉**：定时任务里抛一次未捕获异常，后续调度会永久停止（`scheduleWithFixedDelay` 的经典坑），残留就再也不清了。

### 3.13.5 平台级互斥与冷却

| 机制 | 实现 | 覆盖的问题 |
|---|---|---|
| 同平台互斥 | DB 唯一约束（`platform_id` + `status=RUNNING`）+ 分布式锁 | 手动触发与定时任务撞车 |
| 跨平台并发上限 | 信号量（默认 3） | 同时全量打满数据库连接池 |
| 失败冷却 | Redis 键 + TTL（默认 `超时 + 10s`），值存失败时间戳 | 本端已空闲、对端仍在等的空窗 |
| 冷却提示 | 查询剩余秒数，界面展示"请 N 秒后再试" | 用户点不动却不知道为什么 |

**互斥状态不能放进程内变量**。多实例部署时进程内标志位互相看不见，结果是"每个实例都认为自己空闲"，重复同步同时发生。

### 3.13.6 运行期自检

启动时打印一次实际生效的参数，排查阻塞类问题时不用再猜：

| 打印什么 | 为什么 |
|---|---|
| 连接池 `maxWait` / `connectTimeout` / `socketTimeout` | 级联同步最常见故障是"卡住"，先看超时 |
| 数据库侧 `statement_timeout` / `lock_timeout` / `idle_in_transaction_session_timeout` | 服务端超时若短于客户端，客户端会看到莫名其妙的断连 |
| 本轮生效的闸门阈值、明细上限、保留轮数、审计开关 | 避免"以为开了其实没开" |

只在启动时输出一次（INFO 级），不要每次同步都刷。

## 4.1 功能菜单结构

```

├ 资源共享                    │
│  共享编排      ← 核心：选资源 → 选目标 → 确认（一屏完成）
│  共享总览      ← 按上级看：共享了什么、什么状态

**与需求原文"下级平台 / 上级平台"两套菜单的差异说明**（对应 2.7-1）：

| 原菜单 | 新菜单 | 能力是否保留 |
|---|---|---|
| 下级平台 → 组织管理 / 设备管理 / 通道管理 | 资源中心 → 资源目录（来源筛选"下级"） | 保留，只是不再按方向分两套 |
| 上级平台 → 组织管理 / 设备管理 / 通道管理 | 资源中心 → 资源目录（来源筛选"本地"+"转发"） | 保留 |

| 上级平台的"编码转换" | 资源共享 → 共享编排 → 编码映射（内联） | 保留，但不再是独立菜单（用户不需要为此单独跳页） |

**为什么合并**：一个外部平台在系统里只有一条记录。如果菜单分成"下级平台/上级平台"两套，用户会去两处找同一个平台，且"双向连接"无处安放。合并后用一个筛选解决，能力不减。

## 4.4 平台接入交互

### 4.4.1 新增平台：三步向导（而不是一张 30 字段的大表单）

```
第1步 选类型          第2步 连接与认证        第3步 方向与策略
○ 下级平台（从它收资源） 地址/端口/SIP域/账号    ☑ 允许它向本平台推目录
○ 上级平台（向它发资源） [测试连接] ✓ 已连通    ☐ 本平台向它推目录
○ 仅登记（不传数据）                           同步策略：○手动 ○定时 ●定时+通知
```

- **厂商选择决定默认值**：选"海康"自动填默认端口、默认协议组合（GB28181 同步 + GB28181 取流 或 RTSP），用户只改 IP 和账号。
- **测试连接必须能成功才算配置完成**，避免"配完了发现不通，不知道哪一步错"。
- 方向是复选框（不是单选），因为双向连接合法。

### 4.4.2 平台列表的列

`名称 | 厂商 | 协议 | 方向(收/发) | 状态 | 资源数 | 共享数 | 最近同步 | 操作`

- 状态：`● 在线 / ○ 离线 / ⚠ 异常 / ⏸ 停用`
- 资源数：入站资源数（发给本平台的）；共享数：本平台共享给它的
- 一行同时表达"它给我什么"和"我给它什么"，这就是"一个平台一条记录"的价值

### 4.4.3 同步的交互

- 平台行内"同步"按钮 → 立即创建任务，行内出现进度 `63% · 1240/1980`，旁边"取消"。
- 完成后 toast：`同步完成：新增 12、更新 3、疑似删除 1（查看差异）`。
- "查看差异"打开抽屉，三组列表（新增/变更/消失），消失项可"忽略"（不做删除）。
- 定时同步无需用户参与，但结果必须可见（同步中心有历史）。

| 手动同步 | 行内进度 + 取消；同一平台已有任务时按钮变"查看进度" |
| 同步失败 | 平台行标⚠ + 原因摘要；点开看失败明细（哪一页、什么错） |
| 上游返回空目录 | **不执行删除**，任务标"异常"，提示"上游返回空目录，请确认后手动处理" |
| 大量消失 | 差异超过阈值（如 30%）→ 任务标"需确认"，列出消失项，用户确认后才置 REMOVED |

**最后两条是防止"上游故障导致本地雪崩"的关键交互**：系统不替用户做不可逆决定。

## 5.2 数据库设计建议

| 主题 | 建议 |
|---|---|
| ID | 雪花 ID（`BIGINT`），JSON 输出用字符串避免精度丢失 |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci` |
| 时间 | 统一 `DATETIME`，服务端按 UTC 存储，展示层转本地时区 |
| 软删 | 资源表用 `status + removed_at`，不用 `deleted` 布尔（三态需要） |
| 唯一键 | 必须包含来源：`(source_type, source_platform_id, code)` |
| 树查询 | 物化路径 `path` + 前缀索引 `path(64)`；`parent_id` 索引用于逐层加载 |
| 大表 | `res_channel` 超 300 万行按 `source_platform_id` 分区；`outbox` 按月归档（SENT 超 7 天） |
| JSON | `outbox.payload`、`capability` 可用 JSON 列；查询条件不要依赖 JSON 内部字段 |
| 审计 | 只追加表，按时间分区，保留 1 年（可按合规调整） |

### 5.2.1 单库容量与写放大总预算（M1–M4 叠加后）

前面给的是"什么时候该分区"的触发线，这里补"到顶之前有多少余量"。假设最大规模：**100 万通道 / 5 万设备 / 1000 组织**。

| 数据 | 量级假设 | 稳态体积 | 写放大 | 处置 |
|---|---|---|---|---|
| `res_org` | 1000 组织 | < 5MB | 低 | 忽略 |
| `res_device` | 5 万设备 | ~50MB | 中（同步时只有差异行被 UPDATE） | 忽略 |
| `res_channel` | 100 万通道 | 数据 ~500MB + 索引 ~300MB | **高**：每次全量同步按差异写，最坏 N 行 UPDATE | 唯一需要盯的表；超 300 万行（约 2.4GB）按 `source_platform_id` 分区 |
| `outbox` | 日 1 万次变更 | 保留 7 天约 20MB | **中**：每次资源变更插 1 行，与变更量线性 | 不需要分区，但必须有归档/清理任务，否则长成第二张大表 |
| `sync_round` | 年 1 万轮 | 忽略 | 低 | 保留 1 年 |
| `sync_round_snapshot` | 100 万 × 2 轮 | **~400MB（仅排障期）** | 高 | **默认关闭**；开启时按轮分区，只留 2 轮（3.13.2） |
| `audit_log` | 与变更量线性 | 年 100MB 量级 | 中 | 只追加，按时间分区，保留 1 年 |
| **合计** | — | **稳态 < 1.5GB，排障期峰值 < 2GB** | — | 单库完全够用 |

**三条结论（比数字本身更重要）**：

1. **瓶颈不是体积，是写入次数。** 一次全量同步的写次数约为"有差异行数 × 1.5"（业务表 UPDATE + outbox INSERT）。所以 5.2 的"300 万行"只是近似触发线，真正的判据应该是**写入 TPS 与 DDL/备份窗口**，实测后再校准。
2. **快照是唯一能让体积翻倍的东西。** 400MB 全部来自它，且只在排障期存在。所以"默认关 + 只留 2 轮"不是优化项，是**容量前提**——这也是 6.3 把它放进 C 档的原因。
3. **备份按 2GB 预算。** 每日全备 + binlog 即可，不需要增量备份方案或独立备份库；恢复到任意时点也能在分钟级完成。

## 5.3 SSE / WebSocket 选型

**结论：资源变更对外分发用 SSE；WebSocket 只用于需要双向交互的前端场景（如站内消息、终端）。**

| 维度 | SSE | WebSocket | 判定 |
|---|---|---|---|
| 方向 | 服务端 → 客户端（单向） | 双向 | 资源变更只需单向 → SSE |
| 断线续传 | 原生 `Last-Event-ID`，浏览器自动重发 | 需自行实现 | SSE 明显更优 |
| 重连 | 浏览器内置自动重连 | 需自行实现心跳与重连 | SSE |
| 代理/网关 | 标准 HTTP，穿透性好 | 需要 Upgrade 支持，部分网关不支持 | SSE |
| 鉴权 | 复用 HTTP Token | 需握手阶段自定义鉴权 | SSE |
| 实现成本 | 低（一个 Controller） | 中（连接管理、心跳、会话） | SSE |
| 适用场景 | 目录变更、状态变更、告警 | 双向控制、实时协作 | — |

**本设计的选择**：

1. **对外资源订阅（需求 2.1.3）→ SSE**：订阅方拿到的是"变更事件流"，不需要回执，SSE 完全覆盖，且客户端的实现成本最低（`EventSource` 三行代码）。
2. **前端站内消息/长任务进度 → SSE 或轮询**：进度类用轮询更简单（3 秒一次），消息类可用 WS（已有基础设施的话）。
3. **不使用 WS 承载目录全量**：全量走普通 HTTP 接口（分页），事件流只推增量。

事件格式（与第三部分一致）：

```
id: 10231
event: resource.changed
data: {"scope":"platform:5","refType":"CHANNEL","refCode":"...","changeType":"UPDATE","version":10231}

-- 续传：客户端重连带 Last-Event-ID: 10231 → 服务端从 10232 补发
-- 补不上（超出保留窗口）→ 409 + {"snapshotUrl":"/api/events/snapshot?scope=..."}
```

## 5.4 多厂商协议适配

| 厂商/协议 | 目录同步 | 共享推送 | 取流 | 适配难度 | 说明 |
|---|---|---|---|---|---|
| GB28181 平台（海康/大华/宇视均支持） | Catalog 查询 + Subscribe/Notify | Catalog 响应 + Notify | SIP INVITE + RTP/PS | 中 | **首选统一路径**，三家都支持国标，优先用国标对接 |
| 海康私有（ISUP/EHome） | 私有 SDK/协议 | 私有 | SDK | 高 | 仅在客户强制要求时实现；文档不公开，需商务获取 |
| 大华私有 | 私有 SDK | 私有 | SDK | 高 | 同上 |
| ONVIF（设备级） | Device/Media 服务 | 无（ONVIF 没有平台级联概念） | RTSP | 中 | 只用于"接入设备"，不能用于"平台对接" |
| RTSP | 无目录 | 无 | 直接拉流 | 低 | 只能作为取流方式，不能作为接入方式 |

**关键工程判断**：

1. **平台对接优先走 GB28181**。海康、大华的平台产品都支持国标级联，用国标一套代码覆盖三家，是成本最低的路径。私有协议作为"客户强制要求时的补充"。
2. **ONVIF 只做设备接入**。它没有"平台级联"语义，不要试图用它做上下级。
3. **取流与接入解耦**：即使目录用 GB28181 同步，取流也可能是 RTSP（尤其老设备），所以 `platform` 表要分开存三种协议（3.7.1）。

## 5.5 行业标准分析

### 5.5.1 GB/T 28181 三代演进

| 版本 | 关键变化 | 对本设计的影响 |
|---|---|---|
| 2011 | 首版：SIP 注册、Catalog、INVITE、PTZ | 基础信令模型 |
| 2016 | 引入**业务分组（215）/ 虚拟组织（216）**（附录 D）；完善订阅通知 | **本设计出站目录的核心依据**：给上级看的组织就是 215/216 树 |
| 2022 | 增加**域间目录订阅通知**（附录 N）、PTZ 精准位置订阅、摄像机采集部位类型代码（附录 O）等 | 入站增量可用"订阅"替代轮询；跨域目录同步有标准依据 |

> 说明：以上条款号与变化点来自标准前言及公开解读资料（检索日期 2026-11-23），**落地前请以标准原文核对**，特别是附录编号在 2016/2022 之间有调整（2016 的附录 P 在 2022 中对应附录 N）。

### 5.5.2 对本设计有直接约束的标准要点

| 标准要点 | 设计落点 |
|---|---|
| 平台编码 = `域(10) + 类型(3) + 序号(7)` | 暴露码生成规则（3.9.3） |
| 类型段 200 = 平台/设备，131 = 摄像机通道，215 = 业务分组，216 = 虚拟组织 | 出站目录节点类型判定；入站识别分组行 |
| 目录是 `DeviceID + ParentID` 的扁平列表 | 为什么必须维护虚拟组织树（3.9.1） |
| 目录订阅：`SUBSCRIBE` + `NOTIFY` | 入站增量同步（3.8.1）；出站变更推送（3.9.5） |
| 级联时上级只认"本平台域"内的编码 | 为什么入站资源出站必须重编号（3.9.3） |
| 2022 增加域间目录订阅通知 | 多级级联的增量同步有了标准路径（3.10） |

### 5.5.3 ONVIF

ONVIF 是**设备级**规范（Discovery / Device / Media / PTZ / Events），没有"平台级联"和"虚拟组织"概念。因此：

- 只用于"接入摄像机/NVR"（本地资源的一种来源）。
- 不能用于"下级平台汇聚"或"上级平台共享"。
- 官方在 GitHub 提供规范 schema（`onvif` 组织），可用于生成客户端代码；Java 侧有社区库（如 onvif4j），**使用前需评估维护活跃度与许可证**。

| 5 | **GB/T 28181-2022 标准全文** | 公开托管（如 ossrs 站点提供的 PDF） | 标准原文 | — | — | 核对条款、附录编号、编码规则 | 注意版权与引用规范 |

**调研结论**：

1. **没有找到"完整覆盖本需求"的开源项目**。现有国标平台（如 wvp）解决的是"设备接入 + 单向上级级联"，而本需求的核心是"多来源汇聚 + 多上级定向共享 + 转发 + 来源追溯"，这一层需要自建。
2. **可以直接借的**：媒体层（ZLMediaKit）、SIP/国标报文处理经验（wvp）、ONVIF schema。
3. **必须自建的**：资源来源模型、共享关系模型、虚拟组织映射、Outbox 投递与对账、SSE 分发。

## 5.7 可借鉴的设计与不可复用的部分

| 借鉴点 | 来源 | 如何用在本设计 |
|---|---|---|
| 虚拟组织 215/216 树 | GB28181 2016 附录 D + wvp 实现 | 出站目录的骨架（3.9.1） |
| 目录订阅 + Notify 增量 | GB28181 + wvp | 入站增量（3.8.1）、出站推送（3.9.5） |
| 媒体与信令分离 | ZLMediaKit 架构 | MediaAdapter + ZLM 作为独立媒体层 |
| 设备/通道两级模型 | 行业通用 | `res_device` + `res_channel` 两级 |
| 事务性 Outbox | 分布式系统通用模式 | `outbox` 表 + Dispatcher + 对账（3.9.5、4.7） |

| 不可复用的部分 | 原因 |
|---|---|
| wvp 的"单租户 + 设备直连"资源模型 | 缺少来源隔离与转发，扩展会推翻重来 |
| 开源项目的"通道级手工勾选共享" | 无法表达"共享一个组织（含后续新增）"，运维成本高 |
| 依赖内存重试的推送 | 进程重启即丢，与"数据一致性"要求冲突 |
| 用 WS 推全量目录 | 规模上不可行，且客户端无法增量更新 |

## 6.3 第二阶段：外部平台资源接入

| 项 | 内容 |
|---|---|
| **建设目标** | 一个下级平台的目录可以完整同步进来，只读约束生效，视频可播；且"一次坏报文"不会清空本级数据 |
| **功能范围** | 平台接入向导、GB28181 注册与目录查询、staging 全量同步、订阅增量、三态（STALE/OFFLINE/REMOVED）、同步中心、左树并列展示、入站资源播放 |
| **核心模块** | `adapter/inbound`、`sync`、`resource`（写入白名单） |
| **依赖关系** | M1（且 M1 必须已交付 3.6.6 的原地 UPDATE 写入路径） |

**本阶段拆成两个交付批次，不要混在一起做**（原因：M2a 是业务可见的功能，M2b 是看不见的运行保障，混做会导致 M2b 被压缩到"以后再说"）：

### M2a 同步主链（先跑通）

| 项 | 内容 |
|---|---|
| **交付** | `sync_staging` 暂存表 + 三条集合 SQL 对齐（3.8.2）；三段会话 `start/synching/finish` + 批次 ACK；**单一路径的落地保障**：三条 SQL 方言单测 + 三档规模测试（10/50/100 万）+ 影子对比，以及动作级开关 `sync.delete.mode=mark|real`；只读四层收口；左树并列；入站播放 |
| **关键技术点** | 集合 SQL 的 `SET` 列集与 `WHERE` 差异列集必须**同源生成**（否则出现"数据没变却全量 UPDATE"）；集合 SQL 不落内存 diff（百万级不可行）；`finish` 才切换生效，`synching` 期间线上仍读旧数据 |
| **验收标准** | ① 1 万通道全量 < 5 分钟且可取消；② 分批传输中途断开，重连只重发失败批次，不重复拉成功批次；③ 同一份目录报文分别用内存比对与集合 SQL 跑，结果集逐字段完全一致（影子对比通过），且 PG / MySQL 两套方言单测均覆盖新增 / 更新 / 删除；④ 同一批数据连跑两次，第二次的 UPDATE 影响行数为 0；⑤ 10 万与 100 万两档数据各跑一次全量，无参数上限报错、无锁超时，耗时写明；⑥ `sync.delete.mode=mark` 时只标记不删，切回 `real` 后待删项一次删净 |

### M2b 运行保障（再加固）

| 项 | 内容 |
|---|---|
| **交付（A 缺了会清库，必做）** | 两道删除闸门 G1 空批保护 / G2 批量删除保护（3.8.4）；入站资源原地 UPDATE（3.6.6）；集合 SQL 的 `SET` 列集与 `WHERE` 差异列集同源生成（3.8.2） |
| **交付（B 上线前必须，默认开启）** | `sync_round` 轮次台账（3.13.1，**默认开启，必须落盘**）；组织 4 步回填 + 组织缺失设备延迟重试（3.8.2）；三道残留清理（3.13.4）；平台级互斥与冷却（3.13.5）；运行期自检参数打印（3.13.6，启动打一次 INFO，成本几乎为零） |
| **交付（C 首版可缓，做表与开关但默认关）** | 原始报文快照 `sync_round_snapshot`（3.13.2，**默认关闭，排障期才打开**；涉及 400MB 级表与清理策略，是唯一被后置的交付项） |
| **口径说明** | 台账与快照**不是同一档**：台账是对账依据（每轮一行，长期保留），快照是排障证据（400MB 量级，只留 2 轮）。前者缺了就无法回答"那天为什么没删"，后者缺了只是少一个证据源。所以台账进 B 档，快照进 C 档——这与 3.13.2 的"默认关闭"一致，不矛盾 |
| **关键技术点** | 闸门跳过的是"删除动作"不是"整轮"，且跳过状态必须在 三处可见（台账、同步中心列表、日志）；4 步回填顺序不可调换（本轮命中 → 历史绑定 → 平台根 → `[未分类]`）；审计是**旁路**（异步·可丢·可关），但 **staging 不是旁路**——staging 写失败必须让整轮失败；互斥状态放 Redis/DB，不放进程内变量 |
| **验收标准** | ① 上游回一帧 `SumNum=0`，本级通道**一条都不删**，`sync_round.result` 明写"疑似丢批"；② 本地 10 万通道、本轮返回 1 万条，删除被 G2 跳过而新增/更新照常生效，摘要明写"删除已跳过"；③ 台账 `delete_skipped` + 当时 `guard_ratio` 可回查任意一轮；④ 审计服务关闭（`audit.enabled=false`）后同步成功率与耗时无变化；⑤ **打开快照开关后**连续 3 轮同步，最近 2 轮快照仍在、第 3 轮已清理；开关关闭时该表零写入；⑥ 同一平台并发触发两次同步，第二次被互斥拒绝并给出剩余冷却秒数；⑦ 超过 `sync_task` 保留期的残留 staging 行被自动清理 |
| **验收标准（原有）** | ⑧ 中断后续拉不产生半截数据；⑨ 上游删资源后 STALE→REMOVED 全流程留痕；⑩ 通过任何 API 都无法修改入站资源（含批量接口）；⑪ 入站通道可播放且失败提示带来源 |

**工作量说明**：M2b 约占 M2 的 40%，这是"全做"的口径。按上面的 A/B/C 分层，**A 档 + B 档 ≈ 35% 是 M2 的验收范围**，C 档（仅报文快照）≈ 5% 放到 M2 之后单独做。减负只减了这一项，其余全留：G1/G2、原地 UPDATE、集合 SQL 同源生成这三项缺了会直接清库或锁库；台账、4 步回填、残留清理、互斥冷却、自检是"出了问题能不能查"的前提，也不是可选项。容量依据见 5.2.1 的单库预算表。

## 6.4 第三阶段：下级平台资源对外提供

| 项 | 内容 |
|---|---|
| **建设目标** | 集成方可通过 SSE + HTTP 拿到指定平台的组织与通道，支持断线续传 |
| **功能范围** | 订阅管理、SSE 事件流、全量快照接口、游标续传、scope 鉴权与限流 |
| **核心模块** | `dispatch`、`event_subscription` |
| **依赖关系** | M2（依赖资源变更事件） |
| **关键技术点** | `Last-Event-ID` 续传 + Redis 游标；事件只带定位不带全量；背压（队列上限 + lagged 提示）；多实例扇出；**两形态降级 `CHANGED_DETAIL` / `REFRESH_ALL`（3.11.7）**，阈值 `event_detail_max`（默认 500）；"事件可以合并，游标不能跳号"——降级时也必须发出一条事件占住游标，否则客户端重连会永久落后 |

## 6.5 第四阶段：上级平台资源共享

| 项 | 内容 |
|---|---|
| **建设目标** | 本地资源可共享给多个上级，上级能拉到目录并点播，失败可见可补；**"上一轮为什么没补齐"能靠台账回答** |
| **功能范围** | 共享编排（一屏三段）、虚拟组织树（215/216）、一键生成、编码映射与冲突处理、Outbox 投递、推送记录、对账任务、撤销；**推送轮次留痕**（对齐 3.13.1 的"状态可重跑、事实不可重写"） |
| **核心模块** | `share`、`publish`、`adapter/outbound` |
| **依赖关系** | M1（可与 M2 并行；转发需 M2） |
| **关键技术点** | 同事务写资源+Outbox；暴露码单调分配与墓碑；平台离线暂停队列；对账阈值与全量重推；`SUBTREE` 规则 + 排除行；**推送轮次台账 `publish_round`**（目标平台 / 应推条数 / 实推条数 / 失败条数 / 是否降级 / 错误摘要，与 `sync_round` 同口径但独立建表——一个是入站事实，一个是出站事实，不混用）；**超量降级**：单轮待推 > `event_detail_max` 时合并为一条 `REFRESH_ALL` 推送 + 引用快照，不做逐条循环；平台级互斥与冷却复用 3.13.5（不放进程内变量） |
| **验收标准** | ① 上级目录结构与配置一致；② 断网 1 小时后恢复，自动补齐且无重复；③ 撤销共享后上级目录同步移除；④ 推送失败可见原因并可重试；⑤ 对账能发现人工篡改并纠正；⑥ **任一历史轮次可回查"应推 N / 实推 M / 失败 K"与当时阈值**，能回答"上一轮为什么没补齐"；⑦ 关闭 `publish.audit.enabled` 后推送成功率与耗时无变化（旁路可关）；⑧ 一次共享 2 万通道只发 1 条 `REFRESH_ALL`，上级按快照对齐 |

## 6.6 第五阶段：多级平台级联与资源转发

| 项 | 内容 |
|---|---|
| **建设目标** | 入站资源可共享给多个上级，且不会形成环路；媒体链路可用 |
| **功能范围** | 转发选资源（来源切换）、四道防环、两级媒体串联、状态跟随（上游离线→上级收到 OFF）、跨级映射 |
| **核心模块** | `share`（来源校验）、`publish`、`media`（串联）、`adapter` |
| **依赖关系** | M2 + M4 |
| **关键技术点** | 反向共享检测（目标 == 来源）；`origin_chain` + `hop_count`；会话双向绑定（上游 BYE 触发下游 BYE）；带宽按 2 倍估算；**每跳独立的互斥与冷却**——同一通道的入站会话与各出站会话各持一把锁，不能共用一个通道级锁，否则上游一个断线会把所有上级的点播一起锁住；**3.11.5 的三条硬约束全部落地**：回给上级的 SDP 由本平台构造（`sdpRewritten=true` 可断言）、两侧 SSRC 分别落 `GbInviteSession.ssrc` 与 `CascadeSendSession.ssrc` 并由 `srcStream` 关联、`GbInviteSession.lastRtpTime` 超阈值后按 `by_src` 索引逐个停推 + BYE。**回 200 前的两道校验**：对外地址按 `cascade.sdpPublicIp` → `MediaServer.streamIp` → `hostIp` 解析，拿到空 / `0.0.0.0` / `127.0.0.1` / `::1` 一律回 500 并回收已拉起的取流（私网地址只 WARN）；`m=` 端口必须 > 0——UDP 与 TCP-passive 在回 200 前预分配 `localSendPort` 写进 SDP，ACK 后按同一端口 `startSendRtp`，被 ZLM 报占用则换端口重试最多 3 次并 WARN |
| **验收标准** | ① A→本→B 可播；② 把 B 的资源推回 B 被拒绝且有明确提示；③ 3 跳以上被拒绝；④ 上游**正常 BYE** 后本平台主动清理下游会话；⑤ 转发压测：50 路并发下 CPU/带宽符合预期；⑥ **拔掉来源平台的网线（对端不发 BYE），在该上级的生效阈值内（默认 30s）上级必须收到断流（停推 RTP 并下发 BYE），且本平台两侧会话对象都已清除**——`GbInviteSession` 与对应 `CascadeSendSession` 都不存在、`by_src` 索引为空、ZLM 上无残留流。这条比并发压测更能暴露真实问题，是 3.11.5 第 3 条约束的验收口径；⑦ **抓 200 OK 的 SDP 逐字核对**：`c=` 与 `o=` 等于配置的对外 IP（节点有私网 IP 时必须仍是 `sdpPublicIp`），`m=` 端口 > 0，且报文里不出现来源平台/设备的任何地址；把 `sdpPublicIp` 故意配成 `127.0.0.1` 时点播应返回 500 并在日志给出可读原因，而不是回 200 后黑屏 |

## 6.7 第六阶段：视频业务完善与系统优化

| 项 | 内容 |
|---|---|
| **建设目标** | 视频业务齐备，系统可观测、可运维 |

| 范围蔓延（把播放/存储/智能分析都塞进来） | 工期失控 | 严格按 2.6 业务边界，超出范围单独立项 |

**第 13 项结论与理由**（原为待确认项，现已按"不要求、字段占位"定稿）：

首版不启用 GB35114，但 `platform_credential` 建表时**必须带上 5 个占位字段**（全可空，默认 `cipher_suite='NONE'`）：`cert_id` / `sm2_priv_ref` / `sm4_key_ref` / `cipher_suite` / `expire_at`。理由：占位成本几乎为零，而定表之后再改是重活。

若客户后续提出要求，需要重估的是**四处**，不是一处：

| 影响面 | 后续要改什么 |
|---|---|
| 表结构 | 占位字段填值即可，不需要改表（这就是占位的价值） |
| 入站鉴权 | SIP 注册从摘要认证升级为双向证书（TLS + 证书校验），要补证书签发与吊销流程 |
| 出站推流 | 国密加密的媒体流 ZLMediaKit 是否支持、走 SFU 还是旁路加密模块，决定 M5 媒体串联方案能否沿用 |
| 项目边界 | 若确认要求，应作为**独立里程碑**单列，不要塞进 M2——它同时动 SIP 栈、媒体栈和证书运维 |

**字段占位的具体写法**：

```sql
-- platform_credential 建表即带（首版不启用）
cert_id       VARCHAR(128) NULL,
sm2_priv_ref  VARCHAR(256) NULL COMMENT '密钥引用，不存私钥本体',
sm4_key_ref   VARCHAR(256) NULL,
cipher_suite  VARCHAR(32)  NOT NULL DEFAULT 'NONE' COMMENT 'NONE / SM2_SM3_SM4',
expire_at     DATETIME     NULL COMMENT '证书到期，需提前 30 天告警'
```

# 附录 C　术语表

| 术语 | 含义 |
|---|---|
| 平台连接（platform） | 本平台与一个外部平台的一条接入关系 |
